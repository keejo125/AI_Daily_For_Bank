# 把 Agent 放进任务现场：三个钉钉机器人的工作流嵌入实践

来源：Qoder
原文链接：https://mp.weixin.qq.com/s/0H1uRW7f_V6hFIvKSQTzBw

大家好，我是叶枫，在高德地图做客户端研发。我们用 AI 时，有个很实际的困扰：群里讨论过的事情，还得整理背景再交代一遍；等它做完，又要把结果搬回群里。来回费工夫，还容易漏掉细节。为此，我们把 Qoder CLI 接进了钉钉群，做了三个机器人，分别参与需求澄清、报警分析和代码审查，让 Agent 直接在群里接任务、回结果。接下来就聊聊具体是怎么做的。注：本文中的 Qoder CLI 指的是 Qoder Agent SDK为什么把 Qoder CLI 接进钉钉群我们先从 Code Review，也就是代码审查说起。研发把一份代码改动提交出来，合入目标分支前，需要检查有没有问题。用了 Qoder CLI 之后，只要把 CR 链接和审查背景交给它，后面的取数、审查、出结论，它已经能自己完成。它会读取代码的 diff，也就是改动前后的差异，结合相关源码，对照事先准备的编码规范和判例逐项检查。可放到团队协作里，它仍像一个临时叫来的外援。CR 链接先出现在群里，我们再把链接和背景拷出去；审查完成，还要把结论搬回来。背景在搬运时还会被压缩，之前的讨论和方案取舍容易遗漏。所以我开始关心另一个问题：Agent 应该放在哪里，才能省掉这些转手的工作？这个问题还得拆开。第一，它出现在哪里，才能直接接触任务，不需要我们转述？第二，它要带着哪些业务知识、上下文和工具，才能完成任务？第三，它能管多宽，哪些事可以自己做，哪些必须交还给人？只接通一个聊天窗口，还没有回答完这三个问题。我们的选择是把 Qoder CLI 接到钉钉群里，同时配齐五样东西：出现在现场，接得住上下文，带着知识，动得了手，守得住边界。具体说，需要它时在群里 @ 一下，它能读到任务相关的讨论；业务规则和 Skills 提前配置好，再用工具连接代码、日志、文档等信息。至于哪些操作可以执行、哪些判断必须由人负责，也要一起写清楚。我们希望省下的是重复搬运，不是把人的责任一并省掉。我们做了需求文档、报警分析和业务三个机器人，共用一套底座，各自配置知识、工具和边界，目前都已进入日常流程。它们对应的是研发日常的三个场景：报警群里的信息排查、需求群里的讨论和文档整理，以及业务群里的咨询与代码审查。我们把顺序反过来，让 Agent 守在任务发生的地方。有人在群里 @ 对应机器人，它就带着相关上下文开始处理，做完直接回群，不再经过一次人工转发。报警场景则可以由报警消息自动触发。这里有个重要限制：在现场，不等于始终读取所有聊天。我们只在需要时唤起它，只让它读取这件事需要的上下文。涉及安全边界、需要人承担责任的判断，仍然交给人处理。群聊上下文与机器人的整体架构我们做首购弹窗需求时，群里会先有这样的讨论。客户端研发问，是否只有首购用户才弹，老用户怎么处理？产品确认老用户不弹，之前的方案 B 已经否掉；服务端补充，需要新增“是否首购”字段，预计下周三联调。这时，我们可以 @ 需求文档机器人，让它结合这些讨论、已有产品文档、代码和方案设计，整理开发规格书，再交给编码 Agent 接着做。我看重的是这些短消息连起来提供的背景。谁是产品、谁负责客户端和服务端，大家正在讨论什么，引用了哪次历史讨论，临时补充了什么事实，各个角色又做了什么判断，都在这里。只搬走一句“做一个首购弹窗”，这些信息就丢了。这些讨论构成了机器人的任务背景，接下来要解决的，就是怎么让它带着这些背景去执行。实现上，我们没有给三个机器人各搭一套系统。钉钉机器人通过 cc-connect 连接 Qoder CLI，把群消息转成任务；Qoder CLI 带着对应工作区的配置执行，完成后再把结果发回群里。我们这套实践部署在一台 Mac 上。工作区里，AGENTS.md 规定处理流程和规矩，Skills 提供专项能力，MCP 接入外部系统。架构里还有一层 overlay 包装脚本，负责整理输出、重试和异常恢复等衔接工作。换一个机器人，主要换的是工作区里的内容，底座不需要跟着重搭。三套配置也对应三种不同的边界。需求文档机器人用 doc-write 写规格书、用 doc-check 校验，没确认的问题要列出来，请对应角色回答。报警分析机器人按排查流程提供初步结论，要不要跟进由人决定。业务机器人带着业务清单、CR 规则和判例库，可以查代码并执行允许的合入操作。但高风险、没有先例的问题要升级给研发，release 分支不自动合入。我们是在配置三个岗位，不是给同一个机器人开放所有事情。三个机器人的分工与工作流程先看需求文档机器人。需求群里会有产品、客户端、服务端，也可能有数据研发和测试。我们希望它参与的是澄清需求的过程，而不仅是把聊天记录缩短。它先理解初始需求，发现信息缺口，再在群里追问，把确认的事实和决策写进规格书。产品只讲了主流程，就继续补异常状态和操作边界；端和服务端对分工理解不一致，就把分歧列出来，交给对应角色确认。生成文档后还要过 doc-check，按通用文档规范和业务特性规范检查、评分。缺什么就反馈到群里，补充修订后再检查。达到交付标准，我们才把规格书交给编码 Agent。到这里，需求文档机器人的任务才算完成。报警分析机器人的流程更集中。报警进群后自动触发，它先用 warning-cli 查报警详情和最近走势，再按模块、标签去定位源码，分析可能影响的功能和相关服务接口，给出初步结论。机器人先完成信息收集和初步分析，我们再根据这些证据判断是否跟进、如何处置。至于能否进一步接手判断，要等上下文和能力更充分以后再看。业务机器人承担的事情更多，除了业务咨询和标准化排查，还有日常 CodeReview。我们把它放到 CR 群里，需要审查时，直接贴链接并 @ 它。它通过 Code MCP 拉取最新提交和完整 diff，查相关依赖源码，对照规范和判例库审查，最后把结论发回群里。需要修复的，就列出问题，交给编码 Agent 继续处理；信息不足的，也要明确说出来。审查通过还不等于一定自动合入。只有符合合入策略和权限边界的改动，才会继续执行；release 分支不自动合入，复杂判断、高风险操作和没有先例的问题交给研发。群里如果补充了信息、推翻原来的结论，我们会让它重新审查，并把相应判例沉淀下来。实际使用效果与代码审查数据在 8 月 24 日到 9 月 27 日这五个完整周里，我们的业务机器人完成了 271 个 CodeReview，团队里十多位研发在使用。同期，群里有 308 次 @ 机器人的请求，26 天有请求发生。对我们来说，它已经是日常代码审查流程的一部分。再往下看，除了接了多少任务，还要看它给出了什么结论。再看 268 份 Review 结论的分类。其中 105 份是通过并已合入，90 份是通过、但按策略不自动合入，52 份是合入前需修复的 P1，15 份是阻断合入的 P0，还有 6 份信息不足。P1 和 P0 合计 67 份，占这 268 份结论的 25%。我们在这些审查结论中要求先修复或阻断合入，把问题处理完再往下走。这项统计是按每次回复的结论卡片计算的，同一个 CR 复审会再计一次。所以这里的 67 指的是结论份数，不能当成 67 个独立问题。把三个机器人放在一起看，我能看到它们参与工作的不同深度。报警分析机器人提供调查证据，已经是报警处理流程的一部分；需求文档机器人推动澄清和确认，进入从群聊到规格书的固定环节；业务机器人则继续参与代码审查、咨询和标准化排查。图注：七周302个CR与前文五周271个CR属于不同统计区间。如何为自己的业务找到 Agent 入口做完这些实践，我把经验分成三层：先把 Agent 放进 IM，也就是即时通信群聊；再去看群聊之外的任务现场；最后，为自己的业务选择合适的 Agent 入口。对我们来说，群聊是接入团队上下文成本很低的一步。大家不需要改变讨论习惯，人的角色、任务、历史引用、补充事实和判断本来就在群里。需要帮忙时在群里 @ 一下，结果也回到同一场讨论里，大家可以直接接着处理。但 IM 只是任务现场的一种。代码开发的上下文还在仓库、编辑器和终端里，文档与数据处理的上下文则可能在办公资料里。这些地方同样可以是 Agent 工作的位置。所以，我判断入口的标准很直接：上下文默认存在在哪里，就优先考虑把 Agent 接到哪里。再往行业外延伸，我会把客服的工单系统、历史服务记录，或销售的 CRM、客户档案和沟通记录，作为可能的入口来考虑。问题分类、信息补全、客户摘要等任务，都可以沿着这个思路寻找上下文。客服和销售只是例子，具体接到哪个系统，还得看各自的任务和工作流程。如果要在新的工作流里再做一次，我会先回答五个问题。1. 任务最初在哪里产生？2. 完成它需要的上下文在哪里积累？3. 哪个环节最依赖重复收集、判断或内容生产？4. Agent 的产物由谁、在哪里继续使用？5. 哪些决策和责任必须留给人？对照我们的实践，需求群里形成讨论，规格书交给编码 Agent；报警进群，调查证据交给负责判断的人；CR 链接进入审查流程，结论再进入修复或合入环节。输入、执行和结果的去向，都需要一起考虑。我找入口时，会一起看三件事：任务背景从哪里来，Agent 在哪里执行，结果最后交给谁用。把这些关系理清，再决定用群机器人还是其他方式。模型的能力还会变强，但把 Agent 放到什么位置，仍然是我们要自己做的功课。我们的起点很具体，就是减少群聊与 AI 之间的来回搬运，让需求、报警和代码审查在原来的工作流程里继续推进。从 IM 到任务现场，再到找到适合业务的入口，这是我从三个机器人里总结出的经验。对我们而言，把 Agent 放进任务现场，首先就是让它不再等着人一次次把工作搬到门口。如果你也想试试把 Agent 接进自己的工作流程，可以看看&nbsp;https://qoder.cn/agent-sdk，从一个日常任务开始，把 Agent 用到自己的工作中。我的分享先到这里，谢谢大家！
