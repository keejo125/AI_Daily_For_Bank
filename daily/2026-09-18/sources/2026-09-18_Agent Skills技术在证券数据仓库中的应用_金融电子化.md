# Agent Skills技术在证券数据仓库中的应用

来源：金融电子化
原文链接：https://mp.weixin.qq.com/s/AUpv6xRQXyuwMeZqtM9j2A

文/兴业证券股份有限公司AI创新发展部总经理助理 陈锋
兴业证券股份有限公司AI创新发展部 刘懋霖 张通 林泽钧 李细杰
证券数据仓库既是经营分析、监管报送和客户经营的数据底座，也是高规范场景下的数据治理中枢。围绕我司证券数据仓库分层架构与指标总线体系实践经验，本文提出基于Agent Skills从需求到上线的AI“数字员工”方法：需求界定、口径建模、路径决策、标准化产出、质量前移、运行治理。通过上述技能编排，从AI嵌入到需求理解、建模开发、质量保障和运维交付等关键环节，形成“人定规则、AI执行、结果可审”的协作机制。实践表明，该模式在保证规范性与可追溯性的前提下，显著缩短了开发周期，提高了代码通过率，并推动数仓知识结构化，系统化地向组织资产沉淀。
证券数仓研发的系统工程挑战与 AI 价值
数仓建设不是技术堆叠，而是业务理解、数据治理、工程规范与组织协同共同驱动的系统工程。对证券行业而言，数仓同时支撑经营分析、监管报送、客户经营与风险监测，任何口径偏差、字段误用或调度失配，都可能放大为经营误判与合规隐患。因此，数仓研发天然具有“高复杂度、强约束、低容错”特征，这也决定了研发模式必须从“人力驱动”走向“规则工程化+流程可审计”。
传统模式下，数仓建设核心人力痛点与能力缺口集中在三点（如表1所示）：其一，需求翻译难，业务语言与数据语言之间存在鸿沟，指标拆解与粒度确认成本高；其二，指标治理难，标准化不足时相似指标易重复建设，口径分叉导致报表矛盾；其三，质量保障难，复杂业务约束下问题往往后置暴露，返工与复核成本高。
表1 传统模式的人力痛点与能力缺口
AI在证券数仓中的价值，不止于“更快写代码”，更在于将隐性知识显性化、规则执行流程化、质量控制前移化和结果输出可审计化，帮助团队在效率、质量与合规之间建立稳定平衡。
体系化构建数仓全生命周期能力图谱
为应对上述挑战，我们围绕证券数仓研发全流程构建了体系化数字员工技能，并将其归纳为四类能力模块（如图1所示）。
图1 基于Agent Skills的需求建设架构
第一类是“需求与方案模块”，负责需求理解、数据源定位和血缘追溯，解决业务需求如何快速转化为可信数据方案的问题。第二类是“开发与生成模块”，负责建表脚本、加工脚本和标准化开发产出，解决研发过程中的规范执行与重复劳动问题。第三类是“质量与文档模块”，负责代码审查、设计文档沉淀和质量校验配置，解决交付质量与知识沉淀问题。第四类是“运维与交付模块”，负责结构变更、历史回溯和调度配置，解决上线后变更、回跑和工程部署问题。上述技能并非孤立存在，而是通过编排形成从需求到交付的完整闭环，由六项专业Skills支撑数仓建设中的四大能力体系。
在执行层面，上述基于Agent Skills的需求建设能力落地为“六步法”：需求界定、口径建模、路径决策、标准化产出、质量前移、运行治理。前3步解决“做什么、按什么口径做、走哪条实现路径”，中间1步解决“如何按团队规范稳定产出”，后2步解决“如何把质量和运行治理内建到交付全过程”。其本质是将离散研发活动重构为目标一致、责任清晰、过程可审计的工程系统，使AI从单点提效工具升级为可复制、可推广的数仓研发方法论。
核心场景应用 ：Agent Skills破解证券数仓研发痛点
上述“六步法”在证券数仓场景中的意义，不仅是提升开发速度，更是把口径治理、质量控制与运行治理前置到同一流程边界内，实现效率与合规协同提升，破解证券业务场景下的数仓研发痛点（如图2所示）。
图2 证券数仓研发痛点与数字员工对策
证券数仓具有高复杂度、强约束性与低容错率三个本质特征，对数据的准确性、一致性与合规性提出了严苛要求。高规范性场景下，数据服务于经营、监管与客户等多重目标，定义偏差将引发传导性风险；高复杂度任务中，需求语义到数据语义的翻译常需要多部门协同，一致性保障困难；高风险性后果意味着细微差错即可导致报表矛盾、经营误判、合规风险等问题，呈现“低容错、高代价”特征。
数字员工的引入，正是通过隐性知识显性化、规则执行流程化、质量控制前移化与结果输出可审计化四重机制，系统性地将专家经验沉淀为可复用资产、将质量标准嵌入运行过程、将纠错节点前置至主动预防、将操作链路构建为可追溯体系，从而解决上述痛点，在这些结构性约束中实现从经验依赖到机制保障的方法论跃迁。
下文将围绕四个关键场景，说明该方法如何从需求端、开发端、质控端与运行端形成闭环落地。
1.需求解析与数据源智能匹配
在数仓研发中，最容易出现重复建设和口径分叉的环节往往不是开发本身，而是开发之前的需求翻译。很多需求在业务表述上看似新颖，实则已有相近口径；如果缺少稳定的识别机制，研发人员往往会直接进入编码阶段，最终造成相似指标不断增生。因此，AI数字员工首先建立起“先复用、再改造、后新增”的方案选择机制，把需求翻译从经验判断转变为结构化分析。
这一机制的基础，是把指标、元数据资产等知识纳入同一认知框架。AI先理解需求中的业务目标、关键条件和输出粒度，再去匹配已有口径与历史实现，并给出方案建议。若需求与标准指标高度一致，则优先复用；若与现有口径相近但边界不同，则在既有逻辑上改造衍生指标；只有确无可复用资产时，才进入新增加工路径。其价值不仅在于节省人工“查资料、翻文档、看脚本”的时间，更在于从源头减少重复建设。
2.标准化建模与SQL脚本生成
在方案确定后，关键问题不再是“让AI把代码写出来”，而是“让AI按团队标准组织工程产出”。数仓开发的难点不在语句本身，而在于结构设计、命名方式、参数使用、步骤拆分和运行边界是否一致。若让AI简单地给出一套解决方案，那么显然难以满足上面的需求。
因此我们引入Skills规范，把分散在文档和代码中的最佳实践模板化。无论是结构设计、加工开发还是设计文档沉淀，AI都不从“空白页”开始，而是优先继承团队已有的表达方式和组织范式。由此生成的结果不再依赖随机风格，而更接近团队共享的工程标准。
这一能力的关键，不是单纯“生成更快”，而是“生成即规范、交付即可维护”。
3.代码审查、文档沉淀与数据质量校验
数仓研发的另一个经典痛点，是质量保障长期依赖“开发完成后的人工补救”。很多返工并不是因为需求理解错误，而是因为命名不一致、字段引用错误、边界条件遗漏、上下游口径偏差等问题在开发后期才被发现。AI数字员工在这里并非简单“发现错误再提醒”，而是把质量控制前置到交付过程中，使质量成为研发链路的内建属性。
AI在生成开发产出后，会同步开展结构化审查、文档沉淀和质量规则配置。结构化审查负责识别高风险问题，确保关键字段、关键逻辑和关键边界没有偏离；设计文档自动沉淀需求背景、来源方案和处理逻辑，减少“代码写完再补文档”的信息损耗；质量规则则围绕唯一性、完整性、波动性和一致性等维度形成持续监控。由此，质量控制不再是上线前的一次性动作，而是从开发阶段贯穿到运行阶段。
由此，质量治理从上线前检查转向研发期内建，问题在更早阶段被识别并闭环。
4.可追溯的自动化交付与运维
证券数仓的复杂性还体现在交付之后。表结构会变化，业务口径会迭代，源系统会补录，历史数据会回溯，调度链路也需要持续调整。若这些工作完全依赖个人经验，系统的可维护性就会随着人员变化而迅速下降。因此，AI数字员工并未把能力边界停留在“开发完成”这一刻，而是继续向变更管理、历史回溯和任务上线延伸。
这部分实践的核心，是把运维问题工程化、模板化和可追溯化。结构变更不再依赖临时处理，而是形成带版本标识的标准化变更方式；历史回溯不再是一次性人工拼接，而是按时间区间拆分、按依赖关系编排，确保每一次回补都有边界、有顺序、可追溯；新任务上线也不再完全依赖手工配置，而是基于既有调度模板自动生成配置。由此，AI的作用从“开发阶段的提效工具”延伸为“覆盖研发与运行全周期的工程助手”。
总体看，四个场景对应同一方法论在不同阶段的展开：需求端重治理、开发端重标准、交付端重质控、运行端重闭环，最终形成可复制的智能化研发范式。
实施成效与经验总结
在绩效核算、领导驾驶舱报表等项目的试运行阶段，AI数字员工已初步展现出对研发效能的积极影响。根据早期项目观察：在效率方面，从需求到可运行代码的整体研发周期呈现缩短趋势，其中在指标口径溯源、设计文档输出等标准化环节，耗时有显著下降；在质量方面，因规范执行类错误导致的返工明显减少，代码一次提交通过率得到改善；在知识管理方面，个人经验成功转化为团队可复用的技能资产，为后续项目提供了有力支撑。
更重要的是，AI帮助团队在效率、质量、合规之间找到了新的平衡点。从方法论上看，这一实践至少带来三点启示。第一，AI落地要从技能化而非对话化开始，只有把能力封装为稳定技能，才能形成可复用、可协作的生产力。第二，AI应用要以规则工程化为前提，证券数仓的复杂性决定了模型必须有“边界感”。第三，AI建设要面向组织级资产沉淀，而非个人效率工具。
结语与展望
总体来看，AI赋能证券数据仓库研发，并不是在既有流程外增加一个聊天入口，而是在需求、开发、审查、文档、运维和调度等环节嵌入智能执行能力，重构研发协作方式。对于证券行业这类高规范、高风险、高复用的数据基础设施建设场景而言，AI最重要的价值并非“写得更快”，而是“在写得更快的同时，把口径治理做得更稳、把规范执行做得更严、把知识沉淀做得更深”。
下一阶段，我们将推动该体系从当前以辅助协作为主，逐步迈向更高水平的条件自动化。一方面，继续扩充行业知识库、指标知识库和历史案例库，提升语义检索、口径匹配和方案推荐的准确率；另一方面，探索将元数据、血缘、质量监控和调度配置进一步联动，形成覆盖团队级研发协同的智能能力底座。可以预见，随着相关能力的持续建设，证券数仓研发将从“工程师借助AI做事”，逐步演进为“团队围绕AI重构研发流程”。
