传统运维团队如何定位一次故障
在传统企业里，稳定性和运维团队通常要面对多个业务系统、不同技术栈和分散的数据平台。故障可能来自监控告警，也可能先由业务团队发现。收到问题后，值班工程师需要先确认影响的是哪个应用、环境和时间段，再判断告警是否相互关联、影响范围有多大。运维人员处理一次故障，往往需要在应用日志、监控指标、数据库和知识库之间反复切换，逐项收集信息、判断影响范围并寻找根因。信息分散、排查链路长，故障响应也容易受个人经验和跨团队协同效率影响。
传统的排障链路
1. 告警分诊：
从监控平台查看错误率、响应时间、资源使用等指标，确认故障开始时间、影响服务和严重程度，并排除重复告警。
2. 跨系统取证：
工程师分别进入日志、链路追踪、容器平台、CMDB、数据库和变更记录等系统查询，核对异常指标、错误日志、上下游依赖、近期发布或配置变更。各系统的查询条件和数据格式不同，往往需要人工反复切换和整理。
3. 协同判断根因：
如果问题涉及应用、JVM、数据库或基础设施，运维工程师需要联系对应领域的专家或系统负责人，交换发现并逐步验证假设。告警通常先呈现症状，真正原因可能在下游依赖、资源瓶颈或近期变更中，单看某一个面板很难得出结论。
4. 形成处置与复盘闭环：
定位后，团队整理影响范围、证据、原因和建议；涉及重启、扩容、回滚等生产变更时，按内部流程审批和执行，再观察指标是否恢复，最后补充工单或复盘记录。
这套流程依赖不同方向工程师的经验和多方协同。故障处理中找齐数据、对齐上下文、验证线索等等耗费了大量时间精力才能把最终故障结论传递给相关团队。
AIOPS 高效定位故障
AIOps 并非“用大模型替代监控”，也不是一步到位的无人值守自愈，而是在遥测采集、异常检测、事件关联、服务拓扑等确定性分析底座之上，叠加生成式推理与受控执行，帮助运维团队定位故障根因，给出处置建议和结论。
一、能力从“查看信号”走向“调查问题”。运维 Agent 正从自然语言查询日志、指标，发展到围绕一次故障关联应用、基础设施和依赖信号，形成调查结论与处置建议。
二、数据与上下文是诊断质量的前提。日志、指标、Trace、服务依赖、资源信息及变更记录越完整、关联越准确，调查覆盖度和可解释性越高。
目前 AIOPS 已经在部分企业内部先行落地。让 Agent 承担读信息收集、跨系统数据整理、辅助诊断和报告协同；同时做好数据接入、工具治理、过程追踪和权限边界，再按场景风险逐步扩大自动化执行。Agent 的首要价值，是缩短“发现问题—找到证据—形成判断—传递结论”的链路，帮助用户读取数据，对数据写操作目前阶段还需要企业员工执行。
AgentKit 搭建的 AIOPS 运维系统
已经进入企业开始走进生产任务
针对这一场景，多家企业基于 AgentKit 搭建了 Agent 运维排障系统，并投入日常运维使用。运维人员通过飞书发起排障请求后，由主 Agent 识别问题并分派任务，再调用应用台账、JVM、数据库和知识库等专业 Agent，分别完成领域诊断。
运维人员在飞书群里直接提问，例如：
“生产环境某服务从 10:20 开始大量超时，帮我定位原因，先不要执行变更。”
机器人先回复“已受理”，随后持续给出进度，最后形成一份短而可执行的结论：（以下内容截取自某客户现场示例）
结论：超时主要由下游数据库连接池耗尽引起，置信度高。
证据：
1.10:20 后接口 P99 与数据库等待时间同步上升；
2.
应用日志集中出现连接获取超时；
3.
数据库活跃连接达到上限，慢 SQL 数量无明显增加。
建议：先扩充连接池不是根治方案。建议确认连接泄漏，并在审批后滚动重启异常实例。
风险与数据质量：日志、指标和数据库连接数据完整；本次仅做只读查询，未执行变更。
在运维人员发起问题后，负责把分散的查询和分析步骤组织起来：
1. 接收问题、补齐上下文并路由：
运维人员在飞书群提交故障描述后，主 Agent 识别任务意图并路由到相关专家 Agent。
2. 按专业领域分工处理：
各业务子 Agent 由独立 Worker Agent 承担，Prompt、Skill 与工具按领域收敛。应用台账 Agent 协助定位应用及相关服务，JVM Agent 聚焦 Java 应用运行状态，数据库 Agent 查询数据库侧信息，知识库 Agent 检索已有运维知识。客户现有 HTTPS 等服务可通过 MCP Gateway 接入，尽量保留原有系统形态。
3. 围绕故障现象组织证据：
在该客户的日常使用中，Agent 通过既有工具查询日志、监控，并结合上下游信息进行分析；AIOps 方案还提出按接入情况将 Trace、CMDB 和变更记录纳入交叉验证。以服务超时为例，方案示例会对照接口 P99、应用日志中的连接超时、数据库连接状态等线索，而不是只复述告警。若数据不完整或工具返回异常，也应说明数据质量与诊断边界，避免将“没有查到”误当成“系统正常”。
4. 汇总成可协同的诊断结果：
主 Agent 汇总专家 Agent 的发现，形成包含问题判断、关键证据、建议措施以及风险 / 数据质量说明的诊断报告，并推送至相关飞书群聊，附上透视链接供团队查看。运维人员结合报告决定后续处置；涉及生产变更时，仍按既有审批流程由人确认和执行。
整套系统分成四个域，主流程始终是：提问或事件进入 → Agent 协同诊断 → 调用标准能力 → 从存量系统默认只读
1. 运维使用入口：
支持飞书机器人、用户运维门户、API 或告警事件。
2. AgentKit 智能运维域：
SuperAgent 负责理解、分工与汇总；专业 Worker Agent 负责各自领域的诊断。
3. 标准集成与治理域：
Skill 承载 SOP，MCP 承载工具，A2A 承载 Agent 之间的协作。
4. 客户存量运维与数据域：
继续使用已有日志、监控、CMDB、K8s、ITSM 和自动化平台，不要求推倒重建。
AgentKit Runtime 负责承载 Agent 服务，提供统一部署、健康检查和调用入口；生产侧再配合身份、会话隔离、超时重试、Trace、灰度与回滚，形成稳定运行底座。
这套 AIOPS 智能运维有四个关键点：
会追问：
缺少环境、应用或时间范围时先补齐信息。
有证据：
把日志、指标、Trace、CMDB 和变更记录交叉验证，不只复述告警。
有边界：
数据不足就明确说明；默认只读，高危操作必须人工确认。
可跟踪：
每次工具调用、Agent 协同、失败降级和最终结论都可以审计。
