# OpenViking：让不同 Agent 共享同一套办公上下文

来源：火山引擎Agent社区
原文链接：https://mp.weixin.qq.com/s/0m_OlSoV55nNt9URe-AE9w

蓝字
关注我们！
如今，随着的 AI 工具越来越多，我们往往会在不同的 Agent 之间来回切换：写方案用一个，查资料用一个，分析数据再换一个。团队内成员使用的 Agent 也不尽相同，资料和经验因此分散在各个工具中。
这就导致工具看起来丰富了，协作效率却没有同步提升。一个 Agent 产出的结果和沉淀的方法，很难被另一个 Agent 直接使用。每换一个 Agent，我们都要重新上传资料、解释背景。
而 AI 办公效率的差距，不在于使用多少个 Agent，更在于它们能否共享信息、复用经验，并延续完整的工作上下文。
OpenViking 要补上的，正是这道跨 Agent 的上下文断层。
OpenViking 是面向 AI Agent 的统一上下文数据库。
它是位于不同 Agent 背后的共享 Context 层。豆包、Trae 等都可以接到同一个 OpenViking 上读写，即使 Agent 工具换了，上下文也可以一直延续。
OpenViking 把办公过程中产生的信息分成三类，统一组织成一套带路径的目录和文件：
类型
回答的问题
Resource（资源）
事实和来源在哪
Memory（记忆）
过去沉淀了什么经验
Skill（技能）
做事的方法是什么
面对一个新任务，Agent 不需要把所有历史材料一次性塞进上下文，而是按需分层加载：先读
L0 摘要
判断哪些目录相关，再看
L1 概览
了解关键背景和当前状态，只有核对细节时才加载
L2 完整内容
。任务结束后，Session Commit 会从这次对话和执行过程中提取值得长期保留的偏好、方法和经验，自动写回 Memory。
所以，资料只需导入一次。之后都可以接上同一套上下文继续工作。
一个 Agent 的产物可以写回 OpenViking，成为下一个 Agent 的输入；一个人沉淀的方法，也可以一直迁移复用。
下一次，不必再把同一批材料发给不同 Agent，也不必在每个工具里重新解释这个项目是什么。
01
三个工作瞬间，延续同一条上下文
1. 新人接手：降低交接与上手成本
小 M 作为新人，今天第一天入职，需要接手一个正在推进中的项目。在过去，新人 landing 总是格外痛苦，几十份文档不知道先看哪一份，十几个群聊分不清是在做什么，而在信息量爆炸的超长交接会上，总是听的时候频频点头，结束后依旧一脸蒙圈。遇到不懂的也还得到处问人，甚至有时候连该问谁都不知道。
但有了 OpenViking，小 M 不需要再从几十份资料里盲目摸索。她不仅能读取项目资料，还能继承上一位负责人沉淀的经验和 Skill。她在 Agent 中输入：
请读取 OpenViking 中与客服助手项目相关的 Resource、Memory 和 Skill。
并输出：
1.
用一句话说明这个项目要解决什么问题；
2.
项目当前阶段、目标指标和首期范围；
3.
关键决策时间线，并说明每项决策背后的原因；
4.
当前团队分工，以及遇到不同问题应该找谁；
5.
已完成、进行中、当前风险和待确认事项；
6.
上一位负责人沉淀的经验和踩坑记录；
7.
当前可以直接复用的 Skill，以及每个 Skill 的适用场景；
8.
我第一周建议阅读的文件和建议完成的事项。
每条关键结论后附上真实路径，方便我回到原文核对。
请明确区分“已确认”“讨论中”“已失效”和“缺少依据”的信息。不确定的地方直接标注，不要替项目补充结论。
新人能根据已有材料了解背景，快速上手
几分钟后，小 M 就很快了解了整个项目的背景和进度，理清了每个同事的角色分工，看到团队沉淀的经验，不用先读完所有文档，就能快速理清项目到哪一步、哪些资料有效、遇到问题该问谁。
2. 团队协作：共享项目背景，不同角色在不同 Agent 中接力产出
周三下午，小 M 需要推进“智能客服工作台”的需求上线。这需要产品梳理需求、设计产出交互方案，再由研发评估和实现。真正动手之前，大家得先弄清楚：客户遇到了什么问题？之前讨论过哪些方案？哪些已经确定，哪些还需要确认？
过去，光是对齐这些背景，就要花掉不少时间。每个人都熟悉自己负责的部分，但想了解项目全貌，就得翻文档、查记录、到处问人。更可惜的是，团队明明做过类似的业务，却没有把经验完整地留下来。哪些方法有效、哪些坑需要避开、哪些方案试过却行不通，没有沉淀成方法论，等到再次遇到类似需求，其他人依然缺少可参考的经验，只能重新摸索，甚至把以前踩过的坑再踩一遍。
OpenViking 可以将团队内分散的资料统一组织起来，把原始文档沉淀为 Resource，把历史决策、项目状态和踩坑经验记录为 Memory，再将 PRD 框架、评审规则和协作流程等整理为可复用的 Skill。
团队成员可以将 OpenViking 接入各自熟悉的 Agent，且可以共享同一套项目上下文。产品整理的需求可以直接成为设计的输入，设计完成的方案可以继续交给研发评估；研发发现的限制也能写回项目，供产品和设计调整。有新成员加入时，也能快速了解项目背景、关键决策和团队已有的方法，不必再从头问一遍。
资料只需整理一次，背景可以持续共享，经验和方法也能在不同成员、不同角色和不同 Agent 之间不断复用。

请先整理一份需求梳理结果，包括：
用户是谁，在什么场景下遇到了什么问题。

已确认的首期范围，以及明确暂不纳入的内容。
历史上讨论或否决过的方案，以及对应原因。

请将“已确认结论”和“仍在讨论的方案”分开呈现，每项关键结论附上来源路径。如果不同资料之间存在冲突，请列出冲突及来源，不要自行选择。资料没有说明的内容标注为“待确认”，不要补充推测。
Agent 根据已有资料完成需求梳理。小 M 确认后，将最新的需求范围和决策原因写回 OpenViking。
设计继续产出交互方案
设计师不需要等待小 M 再开一次需求讲解会。他在 Codex 中接入同一个 OpenViking，让 GPT 根据所有的历史信息进行理解，并快速出了一版设计方案，未确认的地方，也会单独列出并指明找谁确认，降低了沟通的成本：
请读取“智能客服工作台”项目的最新 Resource、Memory 和交互设计 Skill。
基于已确认的用户需求和产品范围，输出完整的页面结构、核心操作流程、页面状态、异常情况和交互规则。
历史上已被否决的方案不要重新采用。仍未确认的问题单独标注，并说明需要找谁确认。
Agent 不仅知道要设计什么，还理解方案背后的决策依据、业务约束和异常处理原则。设计师可以直接在这些已确认的背景上继续工作，不必重新翻找会议纪要，设计原则也会回写沉淀到 OpenViking 的 memory 中，方便下一次复用。

OpenViking 企业版：团队共享与资源隔离
OpenViking 企业版进一步支持团队知识共享与资源隔离。 它可以帮助团队建立统一的知识与经验空间，让经过授权的成员和 Agent 共享项目资料、历史决策、工作方法与 Skill。这也为团队管理提供了新的协作方式：管理者可以汇总组员一周的 Agent 记忆与相关资料，了解项目进展、识别协作卡点，帮助项目更好地推进。

3.
个人办公：从周报总结到个人 Skill 沉淀
入职第一周，小 M 就在 Codex 里设好了定时任务：每周日晚上 7 点，自动整理本周工作，生成周报。可到了这周日，7 点过去了，周报迟迟没来。她打开 Codex 一看，才发现本周的可用额度已经耗尽，任务没能完成。
但小 M 却泰然自若，因为她这一周的工作记录和上下文，都已经沉淀在 OpenViking 空间里。 项目资料、关键决定、最新进展，都可以被下一个获得授权的 Agent 继续读取。
于是，她将 OpenViking 接入 Trae，输入下面的 prompt 并创建定时任务, 几分钟后，一份可以直接审阅和转发的周报便生成了：
创建一个每周日晚上 7 点运行的周报定时任务，创建后立即试跑一次。
优先遵循我已保存的周报格式与写作偏好。生成前，读取我的角色、职责、目标、重点项目和汇报对象；检索我有权访问的全部相关空间中的本周工作记录与关联产物，必要时参考近四周背景。不要将检索范围局限于当前对话或工作区，也不要按记录多少判断项目重要性。
根据我的职责和汇报对象，选择合适的表达层级。没有自定义格式时，按以下结构生成：
本周进展 ：选取最重要的 3—5 项结果，写清实质变化、当前阶段及其意义；证据不足时可以少写。
问题与风险 ：说明关键问题、影响，以及需要推动、协调或决定的事项。
下周计划 ：围绕预期结果展开，衔接本周目标与风险，并写明完成标准。
事实以有证据支持的最新明确状态为准。准确区分研究、草案、待评审和已落地，不把计划写成成果，不编造缺失信息；过滤普通维护、琐碎过程和过期状态。
输出前，从接收者视角检查成果是否清楚、风险是否明确、计划是否衔接，以及是否符合我的偏好，修改至通过。只输出可供我审阅、转发的周报，不展示检索与检查过程，除非我要求附上来源。
若信息不足，首次试跑时向我询问关键缺口；后续定时执行时，简要说明缺少什么，不用零碎事项凑数。

在与内容创作者的每一轮对话中，判断当前需求是否需要使用“创作历史记忆 / 个人偏好 / 内容规范 / 风格描述 / 数据复盘”。如有需要，优先利用 OpenViking 的
`search`
召回相关记忆，并以召回内容作为生成、改写、排版和选题建议的默认依据。

`remember`
提炼并存储为个人创作偏好；不要记录仅适用于某一篇文章的主题、案例、数据或临时要求。
