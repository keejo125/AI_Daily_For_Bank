# Qoder Cloud Agents最佳实践：从 Model API 到 Agent as a service

来源：Qoder
原文链接：https://mp.weixin.qq.com/s/sCNqJtwAcP9BE59xcnVRLg

标准化才能支撑规模化，Qoder Cloud Agents 提供模型调用、工具执行、运行环境、用户身份、个人配置、会话和定时任务等能力，将云上harness标准化，以完整的 Agent as a Service 交付，而非仅提供 Model as a Service，降低大模型接入与应用开发的复杂度，让企业直接接入云端 Agent 服务。 企业接入自己的业务工具和用户体系，即可通过 App、网页或 IM 向终端用户提供服务。
用 Qoder Cloud Agents
让 Skill 和 CLI 直接服务用户
Qoder Cloud Agents 提供 Agent 运行与管理能力，并配备云上沙箱执行 CLI、脚本和工具。企业接入已有业务能力后，就可以由 Agent 为用户完成任务直接交付结果，并且云上沙箱可以承载十万级并发 Sandbox，会自动根据任务情况按需拉起或释放执行环境。Agent as a service更细化一些，可以分为：
Skill as a Service：
将分析方法、诊断流程等专业能力封装为 Skill，由 Agent 按流程执行，向用户交付分析报告、诊断结论等结果。
CLI as a Service：
将已有 CLI 接入 Agent 的云上沙箱，向用户提供其背后的业务查询和操作服务。
两者可以组合使用：Skill 定义处理步骤，CLI 执行业务操作。Qoder Cloud Agents Forward通过模板复用这套服务，并按用户管理配置、会话和定时任务，如下图所示：
图 1：企业接入自己的业务能力和用户体系，由 Qoder Cloud Agents
Forward 组织 Agent 服务。
多个用户可以共用一个模板，各自保留配置、会话和任务安排。
跨会话的偏好可以结合记忆能力保存，例如报告语言、关注范围和输出格式。
快速搭建 Agent 服务
企业把企业把 Skill 和工具配置成助手后，还需要让用户方便地找到它、持续使用它。
Qoder Cloud Agents 提供了开源项目 Qoder Cloud Agents Quickstart，包含助手配置、对话、个人记忆和定时任务等功能，企业可以在此基础上接入自己的业务。
配置助手，开始对话
企业可以直接在 Quickstart 中创建和配置模板，管理 Skill、文件、环境和密钥等资源。接入业务所需的工具后，选择模板并点击“使用此模板对话”，即可体验助手处理业务的过程。
模板还可以绑定 Skill、文件和密钥，并设置可用工具及审批策略。企业统一维护这些配置，用户选择助手即可开始对话。
图 2：助手配置。左侧为名称、模型、提示词与运行环境，右侧为技能、资源与工具配置。
同一个助手，为不同用户服务
用户 A 和用户 B 可以使用同一个模板，但关联各自的配置、会话、记忆和任务。例如，有人只要简短结论，有人需要完整报告，可以分别保留自己的偏好。
Forward 用 Identity 关联企业已有的用户 ID。企业接入自己的用户体系后，就能在共用一套服务能力的同时，分别管理每位用户的数据和使用记录。
经常要做的事，交给助手定时完成
每天查一次数据、每周整理一份报告，都可以设成定时任务。用户在应用中填写要做什么、什么时候做，关闭网页后，任务仍会按配置执行。
同一套模板可以为用户 A 每天生成报告，为用户 B 每周汇总一次。企业可以把它做成“订阅日报”或“每周汇总”按钮；启用相应工具后，用户也可以直接在对话里说出任务和时间。
任务结果可以查看，也可以在配置投递目标后送到相应渠道。这样用户不用每次回来重复提问。
在用户熟悉的入口提供服务
Quickstart 通过网页提供这些功能，方便进行调试。在正式接入时，企业可以将对话放进自己的 App、网站，也可以接入 IM，让用户在常用的聊天工具里使用助手。不同入口都需要关联到正确的业务身份，才能访问和接收本人的数据。

场景示例
企业可以将已有工具、数据和专业经验接入 Qoder Cloud Agents，在自己的产品中提供 Agent 服务。从按需查询、分析问题，到定期生成报告，下面几个场景展示了不同业务的接入方式。
场景一：券商分析助手
券商通常已有查询持仓和行情的工具，也有自己的分析方法。要让客户直接用起来，可以把分析方法写成 Skill，将 CLI 放到 QoderCloudAgents 的云上沙箱中运行，只需要将企业自己的用户体系和Qoder的identity做关联，就直接拥有了可以直接对客提供服务的Agent。
比如，客户问“我的持仓是不是太集中了？”，Agent会查询其授权账户的持仓，按个股、行业整理占比，解释集中在哪些地方。客户接着问“哪些股票对今天的涨跌影响最大？”，Agent再查询行情，结合持仓继续分析。
客户也可以订阅每周一至周五上午 9 点的持仓简报，或保存“先给结论，再列数据”这样的阅读偏好。Qoder Cloud Agents 按用户管理这些偏好、会话和任务，券商维护一套助手，就能分别服务不同客户。若涉及辅助交易，订单确认与风控仍走券商原有流程。
图 4：持仓简报的定时任务配置示例，每周一至周五上午 9 点执行。实际运行需接通券商工具与账户授权；若按交易日执行，还需接入交易日历。
场景二：智能门锁助手
门锁厂商已经有开锁记录、锁闭状态、电量和告警等 API，但通常需要用户打开 App，找到对应页面才能查看。接入 Qoder Cloud Agents 后，厂商可以把这些 API 作为助手的工具，配好用户与门锁的访问权限，在 App 中增加一个对话入口。这样就能将已有 API 快速 Agent 化，理解问题、选择接口和整理结果的工作交给 Qoder Cloud Agents。
用户问“今天上午我家有人来过吗？”，助手会查询上午的开锁记录，告诉用户几点开过锁、用了什么开锁方式。接着问“现在锁好了吗？”，就查询当前状态。用户也可以一次问“门锁好了吗，电量还够吗？”，助手分别调用两个接口，再一起回答。
除了随时询问，用户还可以设置“每天晚上 10 点查一下门锁状态”。Qoder Cloud Agents 按时执行查询，配置好通知渠道后，将结果发给用户。厂商沿用原来的设备接口，就能增加对话查询和定时检查功能，不用从模型调用开始搭建整套助手。
场景三：研发线上巡检助手
企业研发团队将接口巡检和日志排查流程编写成 Skill，接入 API 访问、日志查询和工单管理工具，再通过 Qoder Cloud Agents 把助手放进钉钉群，为日常线上巡检提供服务。
值班同学说“每小时检查一次核心接口，有异常就通知负责人”，助手便按计划执行检查。发现接口异常时，Agent 会查询相关日志、给出初步判断，并根据项目责任分工在群里 @ 对应研发，同时创建并指派 Aone 工作项，附上失败明细和排查依据。
通过 Qoder Cloud Agents，团队可以将已有工具和排查经验组成持续运行的巡检服务，把异常发现、初步分析和责任人通知衔接起来。研发同学收到消息后即可查看证据、接手处理，并通过工作项继续跟进问题。
以 SLS 日志查询为例，团队可以在 Qoder Cloud Agents 中上传技能包，并将其绑定到巡检助手模板，让 Agent 按照既定方法查询日志、分析异常。

总结
从 Model as a Service 到 Agent as a Service，企业接入的不再只是模型接口，而是能够调用工具、执行任务的 Agent 服务。Qoder Cloud Agents
提供云上沙箱，以及用户身份、会话和定时任务等能力，减少企业自行搭建和维护 Agent 系统的工作，降低大模型应用的接入门槛。
在此基础上，企业可以通过开源项目 快速上手，体验助手配置、对话、个人记忆和定时任务，也可以参考项目实现，接入自己的 Skill、CLI 和业务 API，搭建面向用户的 Agent 服务。
