# DeepSeek Harness：AI正在从“大脑”走向“工作系统”

来源：Space AIThinker
原文链接：https://mp.weixin.qq.com/s/nSKNkwNkLCQNbltd_NeLpQ

前言
DeepSeek 刚刚开放了 Harness v0.1 开发者预览版，并以 MIT 协议开源。
表面看，这是一个新的 Agent 开发框架；真正值得关注的，是它背后的一个判断：
模型越来越强以后，AI 下一阶段真正困难的问题，开始从“够不够聪明”，转向“能不能持续、稳定、低成本地把事情做完”。
如果把大模型比作发动机，Harness 更像底盘、变速箱、方向盘和仪表系统。过去几年，行业一直在比谁的发动机马力更大；当发动机已经越来越强，问题自然开始往前走：这辆车能不能真正上路，能不能连续跑复杂路况，出了问题能不能恢复，换一个发动机以后整辆车还能不能继续使用。
DeepSeek 给出的核心答案很简单：
一切皆插件。
这五个字，比 v0.1 今天到底有多少功能更值得关注。
01
Harness解决的
是“大模型怎么真正干活”
模型本身擅长理解、推理、生成和规划，但真正完成一件复杂任务，仅仅有模型还不够。
一个 Agent 还要调用工具、读取文件、运行代码、管理上下文、保存状态、使用沙箱、调度子 Agent，并且知道什么时候继续、什么时候暂停、什么时候结束。
这些围绕模型建立起来的运行机制，就是 Harness 所处的位置。
可以把它想成一个能力很强的员工。
这个人再聪明，如果没有电脑、账号、文件、电话、办公系统和工作流程，也很难把复杂工作真正做完。
所以，模型解决的是“会不会想”，Harness 解决的是“能不能做”。
同一个模型放进不同的 Agent 系统，最终表现可能完全不同。
模型决定一个 Agent 能有多聪明，Harness 很大程度决定它能不能把聪明变成行动。
这也是 DeepSeek Harness 最值得看的地方。
它在尝试把过去藏在 Agent 应用内部的“运行环境”，逐渐变成一个可以独立设计、替换和演化的基础设施层。
02
“一切皆插件”：
真正重要的是不把未来写死
DeepSeek Harness 建立在 Cordis 插件系统之上。
模型、工具、Skill、Session、Sandbox、Storage、Loop、Scheduler，甚至 UI，都可以作为独立插件存在。底层框架本身只负责插件怎么加载、怎么卸载，以及彼此之间怎么连接。
插件当然不是新发明，
真正重要的是这种设计背后的态度：
DeepSeek 不想现在就把 Agent 最终应该长什么样写死。
因为不同 Agent 本来就需要不同的工作环境。
Coding Agent 需要 Shell、文件系统和代码沙箱；Research Agent 需要浏览器、搜索和长上下文；数据分析 Agent 需要 Python、数据库和批量计算；面向普通用户的助手，又可能根本不应该开放 Shell 权限。
这就像不同岗位的员工。程序员、研究员、客服、财务，不会坐在完全一样的工位上，也不会使用完全一样的工具。
因此，与其建一个越来越重、什么都包进去的平台，DeepSeek 选择把底层做薄，把上层能力拆开。
可以把它理解成一栋标准化大楼：水、电、管线和接口先统一，里面到底是办公室、实验室还是机房，可以随时重新组合。
“一切皆插件”的真正价值，不是今天功能更多，而是明天换东西的时候不用推倒重来。
这对今天的 Agent 行业尤其重要。
因为模型半年可能换一代，Tool、Memory、Sandbox、Context Engineering 也在不断变化。如果所有能力从一开始就焊死在一起，平台越大，未来调整的成本反而越高。
所以 Agent 基础设施未来真正重要的能力，可能逐渐从“我内置了多少功能”，转向：
我能不能换，我能不能组合，我换完以后系统还能不能继续稳定运行。
03
PTC：
重新划分模型和程序的边界
DeepSeek Harness 里一个很值得关注的能力，是 PTC，也就是 Programmatic Tool Calling，程序化工具调用。
传统 Agent 经常这样工作：
模型先想一步，调用一个工具；拿到结果以后再想一步，再调用下一个工具。
这种方式很灵活，但任务一长，问题也会出现。每一步都要重新调用模型，Token 不断增加，延迟不断累积，每一次重新推理也都会增加新的不确定性。
PTC 换了一种方式。
模型先理解任务，然后生成一段程序，再由程序连续调用工具、处理文件和完成计算。
这就像一个经理不再亲自站在流水线上，每完成一个动作都重新下一次命令，而是先把工作方案写清楚，再让机器连续执行。
真正重要的变化不是“少调用几次模型”，而是：
开放式推理和确定性执行开始被重新分层。
需要理解、判断和规划的部分交给模型；
重复查询、循环、批处理和计算，则重新交给程序。
比如要检查一百份文件，没有必要让模型打开一份、思考一次，再打开下一份、再思考一次。模型可以先生成处理逻辑，让程序把一百份文件跑完，最后只对异常结果进行判断。
所以，成熟 Agent 的标志未必是让模型参与更多步骤，
恰恰相反，可能是：
把真正需要智能判断的部分留给模型，把能够确定执行的部分交还给程序。
未来复杂 Agent 很可能同时使用三种方式：
固定流程交给 Workflow；
动态判断交给 LLM；
大量确定性动作交给 Programmatic Execution。
这不仅影响效率，也影响成本和稳定性。
最好的 AI 系统，未必是模型参与最多的系统，而可能是模型只出现在真正需要智能的地方。
04
Trajectory：
Agent时代，过程开始和答案一样重要
DeepSeek Harness 另一个值得重视的设计，是 append-only 的会话日志。
Agent 在运行过程中看到的系统提示、上下文、工具调用、工具结果、子 Agent 调度等，都会被持续记录下来，并形成完整的 Trajectory，也就是任务轨迹。
这件事情比普通日志重要得多。
因为一个复杂 Agent 最后的结果，往往只是整个过程的最后一个状态。真正决定它为什么走到这里的，是前面几十次甚至几百次判断和执行。
所以 Trajectory 更像 Agent 的“黑匣子”。
出了问题以后，不只是知道“结果错了”，而是可以回放：
当时模型看到了什么；
调用了什么工具；
工具返回了什么；
在哪一步改变了计划；
哪里出现了偏差；
最后为什么得到这个结果。
这首先解决的是工程问题。
Agent 跑了很久以后失败，可以恢复；开发者可以从某一个节点分叉，换模型、换 Prompt、换工具，再比较另一条执行路径；不同策略也可以基于真实轨迹做评测。
但往前再走一步，Trajectory 还可能成为一种新的训练资产。
过去大模型最典型的数据是：
问题 → 答案。
Agent 时代越来越重要的数据可能变成：
任务 → 判断 → 调工具 → 得到反馈 → 修正计划 → 再执行 → 完成任务。
真正有价值的，不再只是“最后答案对不对”，还包括：
一件事情到底是怎样被高质量完成的。
因此，Trajectory 未来可能同时服务三个方向：
运行回放、评测优化，以及训练，
换句话说，Agent 时代的数据资产正在从“答案”向“过程”扩展。
05
对私有化行业最大的启发：
企业要掌控的，不再只是模型
对于银行、证券、保险、运营商、能源、制造、政务等高度重视私有化部署的行业，DeepSeek Harness 所代表的方向尤其值得关注。
过去谈 AI 私有化，大家最常问的是：
模型部署在哪里？
GPU 在哪里？
数据出不出域？
但进入 Agent 阶段以后，这已经不够了，
因为 Agent 不只是调用模型，
它还会访问企业数据库、业务系统、文件、账号和 API，会运行代码、保存 Memory、维护 Session，也会留下大量执行轨迹。
所以企业未来真正需要掌控的，不再只是“大脑”，
还包括它工作的整个环境。
可以把 Agent 想成一个真正进入企业工作的数字员工。
企业不会只关心“这个人的大脑在哪里”，还会管他的门禁卡、电脑账号、能进入哪些系统、能读取哪些文件、能不能访问外网、能拿什么凭证去执行操作，以及做过的事情能不能追查。
Agent 也是一样，
所以私有化 AI 正在发生一个很重要的变化：
过去私有化的主要是 Model，下一阶段企业需要掌控的是整个 Agent 运行环境。
这里的“私有化”也不必狭义理解成所有组件都必须物理部署在本地机房，
更准确地说，是：
运行边界由企业定义；
数据和权限由企业控制；
关键凭证由企业管理；
执行过程能够被审计；
核心组件可以被替换；
出了问题能够定位、隔离和恢复。
这已经远远超过“把一个模型搬进机房”。
06
企业真正需要的
是“能换、能管、能追”
插件化对企业还有一个更现实的价值：降低技术锁定。
今天可能使用 DeepSeek，明天可能增加 Qwen；某些场景使用通用大模型，另一些场景使用专用小模型；语音、图像、Coding 又可能分别采用不同技术。
对于一个准备运行五年甚至十年的企业 AI 底座而言，最重要的问题未必是：
“今天有没有选中最强模型？”
而更可能是：
明天出现更好的模型，我能不能低成本换进去。
这就像装修一栋大楼。
真正好的设计，不是今天买到了最好的空调，而是水、电、管线和接口足够标准，以后换品牌不用重新拆楼。
所以企业真正需要避免的，不是今天选错一个模型，而是把未来几年锁死在今天的一次技术选择里。
但“能换”只是第一步，
插件越开放，治理反而越重要。
如果 Tool 是插件，谁批准它访问客户数据？
如果 Sandbox 是插件，它能不能访问外网？
如果 Skill 更新了，新版本有没有测试？
如果模型换了，这一次任务到底用了哪个版本？
如果 Agent 自己生成了一个工具，这个工具能不能直接进入生产环境？
如果某一个插件出了问题，能不能只隔离这个插件，而不是拖垮整套系统？
所以“一切皆插件”真正进入大型企业以后，还必须配套另一句话：
一切插件皆可治理。
模型、Tool、Skill、Sandbox、Credential、Memory、Trajectory，都需要版本、权限、审批、审计、评测、隔离和回滚。
对于企业级 Agent 基础设施来说，真正的成熟不是“什么都能插”，而是：
什么都能换，什么都能管，什么都能追。
07
Agent的运行环境
正在成为新的基础设施层
DeepSeek Harness v0.1 当然还很早。
Cordis 能不能形成稳定生态，插件体系能不能真正发展起来，PTC 在复杂生产环境里的效果如何，都还需要继续验证。
但这次发布已经清楚地提出了一个值得关注的方向。
一个模型能不能持续、稳定、低成本地完成复杂任务？
于是，Sandbox、Memory、Context、Tool、Tracing、Evaluation、Runtime、Harness 开始从应用内部的技术细节，逐渐变成独立的基础设施问题。
原因其实很简单：
模型能力越强，人们越敢把复杂任务交给它；任务越复杂，模型之外的系统工程就越重要。
DeepSeek Harness 真正值得关注的，不是它今天已经做成了什么，而是它正在把一个过去被包在 Agent 应用里的问题单独提出来：
Agent 应该拥有一套可以组合、替换、追踪和治理的运行环境。
对整个行业来说，这意味着 Agent 的竞争正在从 Model 延伸到 Runtime。
对私有化行业来说，这意味着下一阶段真正需要建设的，不再只是一个私有化模型平台，而是一套企业能够长期掌控的 Agent 运行环境。
AI 过去几年一直在解决“怎样变得更聪明”，
接下来更难的问题是：
怎样让这种聪明真正变成可以长期运行、稳定执行、出了问题可以追查，而且随时能够升级和替换的行动系统。
这可能才是 DeepSeek Harness v0.1 最值得关注的地方。
