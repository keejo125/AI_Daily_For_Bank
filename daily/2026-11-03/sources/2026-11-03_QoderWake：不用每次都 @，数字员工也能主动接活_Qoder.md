# QoderWake：不用每次都 @，数字员工也能主动接活

来源：Qoder
原文链接：https://mp.weixin.qq.com/s/KrKXOBOvbbrtCUoVIT_Ing

写在前面项目群里有人贴出一条失败的流水线，接着问：“有谁能帮忙看一下吗？”从单一的Agent解决问题的角度而言，当前针对已经具备项目访问权限和研发工具的 Waker，排查这条流水线并不困难。但在之前的协同链路中，如果没有明确@Waker干活的信号出现，Waker并不知道这句话是在找我，还是同事之间的对话？有人已经接手了吗？如果现在我接手任务，是能帮上忙，还是打断别人？这一个非常常见的工程研发的场景，其实就已经反映出了数字员工在接入真实工作场景时的几个核心痛点问题：数字员工该如何在复杂的群聊背景下，快速、主动地去响应属于它的任务？主动响应的能力如何在保证质量的情况下，不显著增加用户的成本？在正式展开介绍 QoderWake 数字员工的主动响应能力之前，我们首先需要理解与Personal Agent的核心区别。对于Personal Agent而言，它同样可以读取群聊消息、主动替用户回复，但它通常围绕用户个人的目标和偏好，判断一件事是否值得参与；而在组织协作下的数字员工则被授予了独特的职责，并且需要在多人的复杂并行讨论中确认需求来自谁、交给谁，以及自己的行动会影响哪些人。发送人身份、mentions、回复关系和职责策略，都是为这个判断提供依据。因此，对于数字员工来说，群聊里的主动性，首先是判断何时该由我承担责任，而不只是发现有事可做。QoderWake 的 @Waker 能力已经支持了数字员工能够在群聊里交办工作，而主动响应也沿用了这套任务系统，升级加入了事件接入、行为判断和路由决策，实现了群成员不必每次都重新点名，也能让数字员工在合适的时机对合适的问题进行响应。在主动响应之前，Waker已有的三类各有用处的入口：@ 把执行者交代清楚条件响应覆盖已知规则定时响应处理按计划发生的工作它们先让任务能够稳定地进入系统，但仍需要人点名、提前写出规则，或者设定时间。临时出现、表达各不相同的求助，很难全靠这些入口覆盖。怎么让数字员工能够处于大量群聊消息的记录中，找到自己合适的参与时机，做出合适的响应，就成为了主动响应的设计初衷。主动响应的方案设计主动响应沿用已有的 @Waker 任务系统，增加消息接入、初筛和路由判断。这里最重要的划分，是先发现可能的工作，再确认责任，最后投入资源执行。整个过程可以分成四个部分：接收来自群聊的新消息决策模型（如JEV模型）快速初筛，判断哪些新消息值得进入完整路由通过初筛的继续由 Router 决定任务是否正式触发，并决定归属，再交给 Work 执行最终触发的结果主动发送至群聊，响应对应任务图 1：主动响应的主要处理链路2.1 群消息的主动获取主动响应由群聊中的新消息驱动。系统接收到消息后，保存发送人、会话、时间、回复关系、mentions 等信息；后续判断始终引用真实消息，不能只把一段脱离来源的文本交给模型。主动响应的上下文我们也做了严格的管控，对于新消息而言，只有最近发生的事件可能会对响应的判断产生最终的影响，而更早的消息会作为上下文背景帮助理解指代和业务语境，但不会独立触发一个新任务，从而防止旧事被重新唤起。2.2 群消息的筛选和过滤群里大多数消息其实属于同事之间的日常交流，并不是真的指派给 Waker 的工作请求，如果把所有消息都一股脑的交给 Router 去进行完整的推理，持续成本会增加，也可能让真正的求助排在日常闲聊后面；只靠“构建失败”这样的关键词，又分不清求助、复盘和成员之间的讨论。对于使用者而言，在开头提及的问题自然而然的出现了：Waker 主动之后，同一项排查会不会更贵？QoderWake 相较于基础的@Waker链路，主要在Router路由前进行了行为判断的预检查，整体上分为程序检查、JEV 快速初筛和 Router 决策三个层次：程序处理确定的条件，JEV 判断是否值得继续理解，Router 再确认职责与任务归属。同样提到“构建失败”，在不同的群聊背景中，Waker 可选择的处理方向完全不同：JEV 接收有效策略、本轮新消息和少量背景，只输出一个初筛分数。当前实现要求严格超过阈值才继续；这个分数不是已校准的请求归属概率或业务成功概率。JEV 不规划执行步骤，也不生成群回复。即使通过初筛，Router 仍需分清谁在请求谁做事：“查完把结果发给 Waker”里的 Waker 是接收者，并不因此成为执行者。2.3 Router 路由机制Router 要回答的是：这是不是当前 Waker 的任务，现在该不该接手？它可以按需检索历史消息、任务和记忆，补足近期上下文，但不在路由阶段直接排查流水线。比如“查完把结果发给 Waker”，说的是结果接收者。即使这条消息很像工作请求，也不能据此把 Waker 当成执行者。理解了意图，还需要确认责任。把路由与执行分开，还有一个实际好处：一次耗时排查不会占住后续消息的路由过程。代码、日志和工具操作进入独立的 Work 上下文，路由只保留判断当前请求所需的背景。。区别于DeepSeek Harness的“everything is plugin”的逻辑，我们还是通过一定量的系统级的上下文管控，保证了模型尽可能少的通过工具获取必须的背景信息，从而增加对于语义理解的鲁棒性。2.4 Waker 执行与结果交付路由接纳后，具体工作进入绑定 Waker 的独立 Work 上下文，使用它的工作目录、模型和已授权工具。Router 不需要等这项工作全部结束，才能继续处理后续路由；执行侧仍受现有队列和并发限制，不能据此理解为无限并行。2.5 主动响应策略的配置策略用自然语言说明何时需要 Waker 参与。例如：群成员明确提出本项目构建失败的排查需求，且没有指定其他执行者。写策略时，一个实用的办法是同时检查正例和反例：哪些求助应该接，哪些相似讨论应该放过。这比只写“积极帮助群成员”更容易执行，也更容易检验。定向交给同事的请求、引用旧记录的讨论，就可以用来检查职责是否写得过宽。用户可以在控制台维护策略，也可以在群里明确要求 Waker 新增、修改或删除。这两种方法，能够让用户在使用主动响应时能够灵活的在多端实现对策略的配置。主动响应策略的自主学习能力3.1 从历史请求归纳策略手动策略适合确定职责。但是每个群从空白开始写策略，有些费力。团队已经反复交给 Waker 的工作，能不能帮助它识别下一次同类求助？策略自学习从这些实际交办中归纳响应条件。例如，成员多次明确交办本项目的构建排查，可以成为归纳这类职责的证据。但某次临时要求查询设备 IP，不能自然扩展为授权它检查所有设备。学习要保留业务对象、适用范围和排除条件；更值得观察的变化，是同一类合理求助不再反复需要点名，同时没有接进来更多无关工作。对于学习的内容，QoderWake 也进行了严格管控，学习依据必须属于当前响应身份，即历史上的结构化 @ 和稳定 ID 用来确认当时找的是谁，而不会只根据昵称判断。在学习过程上，每一天的历史消息，都会在凌晨按滑动窗口分批进入学习，并结合能够对应到来源消息的任务结果与后续反馈。每条新增或改写建议，都需要当前可见的证据，且至少包含一条宿主确认指向当前响应身份的请求。图 2：Dreaming主动学习响应策略在学习链路上，主动响应策略与记忆的Dreaming同时触发，但彼此的进程相互独立，互不影响，从而避免了极端条件下失败任务的连锁反应。3.2 自学习结果的提交与保护人工调整的优先级高于自动归纳。人工新增、通过对话创建，以及编辑后固定的策略，不允许自动学习覆盖；删除会留下抑制记录，防止等价内容又被学回来。自动学习可以单独关闭，已有策略仍继续生效。这些保护解决了“谁有权改职责”，但还没有回答“改完是不是判断得更好了”。QoderWake 也支持了在群聊会话中直接创建或更新主动响应策略的能力，用户的明确交办可以提供归纳职责的正例；“这次交给小张，你先不用跟”、“只看发布失败，不看日常开发构建”这样的纠正，更适合用于收窄边界。主动响应策略成本&amp;耗时评测把 @ 去掉，同一件事会更贵吗？群里的人又会多等多久？本文在钉群中进行了实机测试，通过同样的问题在 @ 与主动响应间的全链路监控，进行了成本及耗时的比较分析。4.1 评测范围与统计口径这次测试里，我们选用了「历史材料的问题判读」、「技术说明的文字整理」、「指定源码的只读核对任务」三种不同类型的任务进行比较分析。同一配对保留完全相同的任务正文与交付要求，区别在于是否真实提及数字员工：@ 触发直接进入 Router；主动响应则先经过消息采集和 JEV 初筛，再交给 Router 判断。职责策略、数字员工和模型档位保持一致，关闭策略自动学习，交替安排两种触发方式的先后顺序，最终汇总一次请求级 Credits。4.2 平均消耗与任务差异先看整体结果：从 Credits 消耗来看：本次主动响应的平均 Credits 消耗基本持平于通过 @ 触发的任务，没有因为增加了主动响应而造成了单轮任务的消耗增加。但需注意：少量轮询通过决策模型初筛的case会进入Router 层产生消耗，该消耗暂不在本次分析中讨论。从平均端到端耗时来看：平均端到端耗时会有略微的增长。但该耗时的增长对应着原先必须用户显性 @ 触发改为了模型主动接手任务的行为改变，属于预期内的略微增长。图3：同任务配对的平均消耗与耗时把资源与耗时放在一起，差异会更直观。图 4：两种触发方式的平均资源轮廓本次主动响应的平均输入、输出用量和 Work 侧耗时都更高，Router 平均耗时则更短，这也说明，主动响应增加了发现和判断任务的工作，但进入 Router 和最终的 Waker 响应之后，实际开销还取决于当时的上下文与执行过程。4.3 链路耗时与运行波动这次把“结果已经发出”和“系统已经收尾”分开计时。端到端耗时从原始消息发送开始，到出站文本被标记为发送成功的落库时刻结束，图 5：平均交付耗时拆解拆开后能看到，主动响应多了 JEV 初筛，但这段在本次交付耗时中占比较小。采集等待、派发准备和 Work 执行的差异同样可见。均值之外，再把每项主动任务与它自己的 @ 结果相比。图 6：相同任务的相对差异可以看出，主动响应的交付等待都更长，消耗却在 @ 参照线上下交错。它并没有表现为一个稳定的“主动附加”，也没有表现为稳定的成本波动，因此还是需要根据实际的上下文背景来讨论消耗，主动响应本身在单一任务上没有显著的消耗提升。主动响应的效果展示QoderWake 的深度用户已经把 @Waker 与主动响应用在了研发告警协作中。在数字员工加入前，处理告警信息对于值班同学而言，一直是老大难的痛点问题：一条“超时”告警，可能代表故障，也可能只是任务运行时间超出了偏紧的阈值。值班同学需要先查上下文，才能决定要不要继续投入。Waker 若已具备相应职责与工具权限，便可以协助人工，先行承担这一步排查和整理。下面的记录展示了两次具体研判：一条重复报警被 Waker 判断为噪声，并给出降低重复告警影响的建议；另一条任务超时报警，则结合近期运行耗时，被判断为更适合继续观察，并提出复查建议。这些是它在当时给出的分析，后续是否恢复、判断是否成立，仍要由监控和实际处理结果确认。图 9：主动响应在实际生产场景中的记录写在最后正如文章的开头所述，随着基模能力的不断演进，数字员工对于特定任务的执行能力已经不是唯一的问题，对于真人员工需要介入的情况也在逐步减少，那么怎么让数字员工能“在合适的时间，做合适的事”？怎么保证主动响应能够随着群聊成员、任务的不断演进也能够快速地实现调整？这一系列问题，都将是我们下一步需要去深入挖掘的方向。QoderWake 也会在这个方向上持续探索和演进，让数字员工能够越来越好的加入到真人员工的工作环境中。
