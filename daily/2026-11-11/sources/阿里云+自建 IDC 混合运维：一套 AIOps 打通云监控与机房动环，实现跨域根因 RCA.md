# 阿里云+自建 IDC 混合运维：一套 AIOps 打通云监控与机房动环，实现跨域根因 RCA

来源：51CTO技术栈
原文链接：https://mp.weixin.qq.com/s/6f4FwD5JGWsSQAW5WCLmSA

我是韩先超，51CTO 学堂 K8s、Python 教学总监、
AIOps
实战训练营讲师，云计算架构师，具有 8 年项目实战经验+5 年教学经验，线上学员已达 300w+。
很多中大型企业运维现在都卡在
一边使用阿里云的公有云、一边自建机房/IDC
的混合架构里。
两套体系各自有监控：云上是云监控、ARMS、SLS；机房侧是传统动环、
UPS
、精密空调、安防监控。
两套系统独立告警、独立台账、独立值班，云归云、机房归机房，出了问题经常 “分头查、各自猜”。
网上大部分 AIOps 文章，要么只讲纯云上微服务链路
RCA
，要么只讲本地机房巡检，很少讲
如何用一套 AIOps 平台把阿里云观测数据和传统机房运维数据进行对接、融合、统一研判
。
本文针对这个差异化场景给出落地
实操
，包括架构、对接流程、真实故障案例、踩坑、收益等。
混合运维的真实痛点：阿里云和机房是两个信息孤岛
我们的架构：核心业务跑阿里云 ECS、容器服务用 ACK、RDS；数据库备份、存储、灾备、物理网关、供电制冷放在自建 IDC 机房。
之前的现状是：
阿里云侧
：云监控告警、ARMS 链路、
SLS
日志、ACK 容器指标，告警推到一个值班群；
机房侧
：动环系统采集电压、温湿度、漏水、UPS 状态，单独一套告警推另一个群；
运维人员要同时看两套平台、两套告警、两套资产台账。
痛点：
1. 故障因果割裂
机房空调故障 → 机房温度升高 → 阿里云专线接入的物理网关过热丢包 → 云上业务大量超时。
故障现象是阿里云 ARMS 疯狂报接口错误、RDS 延迟上涨，但云上监控看不到机房温度、空调状态；机房动环只报空调告警，不知道会影响云上哪些业务。
两边告警分开推送，值班人很难第一时间把 “机房制冷故障” 和 “云上业务报错” 关联起来。
2. 资产无法统一映射
阿里云资产（ECS、ACK Pod、RDS）、机房物理资产（机柜、交换机、UPS、专线设备）没有绑定关系。
想查某个云上业务依赖哪条物理专线、在哪个机房机柜，只能靠 Excel 手工查。
3. 告警风暴叠加，分不清主次
机房一个动力故障，同时触发
动环告警+专线告警+阿里云 ECS 网络告警+业务应用告警
，几十条告警分散在两个渠道，很难识别根因。
4. 变更不互通
机房割接、专线改造、UPS 检修，变更记录只存在机房工单；阿里云发布、弹性扩容记录在阿里云平台。AIOps 无法自动识别 “是不是机房变更引发云上异常”。
5. 运维流程两套标准
云上用云侧工单、机房用本地运维工单，故障复盘、SLA 统计、值班排班两套体系，统计 MTTR、故障影响范围非常麻烦。
很多人会问：阿里云本身有
云监控
、企业监控，机房动环厂商也自带平台，为什么还要 AIOps？
答案很简单：
它们各自只能看懂自己域内的数据，无法跨云-机房做关联推理、根因研判
。
AIOps 在这里的定位，就是统一融合层、事件收敛层、跨域因果分析层。
整体对接架构：AIOps 作为中间融合枢纽
整体思路：
不替换阿里云原有观测工具、不推翻原有动环系统，做对接集成，而不是重建
。
整体数据流如下：
1. 阿里云数据接入层（AIOps 拉取/接收阿里云数据）
云监控
：指标、告警事件（OpenAPI+告警 Webhook 推送）
ARMS
：调用链 Trace、应用错误指标
SLS
：日志，通过 SLS 消费/投递到 AIOps
ACK
：容器指标、Pod 事件、HPA 事件
资产
：ECS、RDS、SLB、专线、云连接网关资产信息，定时同步资产标签
2. 机房传统运维系统接入层
动环主机
：Modbus/SNMP 协议拉取 UPS、配电柜、空调、温湿度、漏水传感器指标与告警
机房监控平台
：摄像头告警、门禁、消防事件
本地运维工单系统、机房变更管理系统
：割接、检修、上架下线变更事件
3. AIOps 核心引擎
资产拓扑映射模块
：建立 “云上业务 → 云专线 → 机房物理交换机 → 机柜 → UPS/空调” 的依赖拓扑
异常检测引擎
：时序基线检测、跨域告警聚类
根因推理引擎
：基于拓扑做跨域因果研判（重点：区分云上自身故障/机房基础设施引发的云上故障）
事件中心、工单闭环、报表 SLA 模块
4. 统一出口
统一事件卡片、统一值班通知、统一工单、统一故障复盘看板。
核心原则：
原有系统继续保留，只做数据单向流出到 AIOps，AIOps 不反向改造阿里云和动环底层，降低对接风险
。
三个真实跨域 AIOps 实操案例
案例 1：机房空调故障，跨云根因自动研判（最经典场景）
背景：
阿里云专线接入设备部署在自建机房机柜，该机柜由精密空调负责制冷。
某天，机房空调故障停机，机柜温度缓慢上升，物理网关芯片过热，专线丢包，最终阿里云上订单服务、RDS 跨库访问大面积超时。
传统处理流程：
运维先收到阿里云 ARMS 大量业务超时告警 → 排查 SLS 日志发现跨专线请求丢包 → 人工去查专线设备所在机房 → 打开动环平台，才发现空调已经停机。整个排查耗时 70 分钟。
接入 AIOps 之后的处理流程
1. 机房动环通过 SNMP 推送【空调停机告警】到 AIOps 事件中心；
2. AIOps 拓扑引擎自动检索这个空调负责哪些机柜、机柜上有哪些专线设备、专线对应阿里云上哪些业务服务；
3. 短时间窗口内，阿里云 Webhook 推送上来一批【专线丢包、应用 P99 延迟上涨、RDS 访问超时】告警；
4. AIOps 基于拓扑依赖关系做因果推理
根因候选：机房精密空调停机（置信度 94%）
衍生影响：机房机柜升温 → 专线网关丢包 → 阿里云侧订单、库存服务跨专线调用超时
影响范围：阿里云 ACK 集群订单应用、跨机房 RDS 读请求
建议：机房现场恢复空调，云上可临时切备用专线
5. 只推送一条汇总事件卡片，附带：动环空调指标曲线、机柜温度曲线、阿里云专线指标、受影响云上服务清单。
值班工程师拿到结论直接处置，本次 MTTR 缩短至 12 分钟。
踩坑点：
坑
：一开始只做告警汇聚，没有做资产拓扑绑定，AIOps 只能把告警堆在一起，分不清因果，只是一个消息合并机器人。
方案
：提前梳理专线、物理设备、云上服务的依赖关系，维护拓扑。注意拓扑是跨域 RCA 的基础。
案例 2：UPS 电池劣化预警，联动评估云上业务风险
背景
：机房 UPS 给专线、核心交换机供电，是阿里云专线的后备电源。动环只能看到电压，单节电池缓慢劣化很难发现。一旦市电中断，UPS 撑不住，云上业务直接断连。
AIOps 实操方案
1. AIOps 持续从动环拉取 UPS 每一节电池内阻、电压、温度时序数据；
2. 时序异常算法学习基线，识别内阻持续漂移，输出电池健康度 SOH；
3. 一旦识别电池劣化隐患，AIOps 自动查询拓扑：这台 UPS 承载哪些专线，对应阿里云上哪些核心业务；
4. 生成分级预警工单，标注：隐患位置+关联云上业务等级（核心交易/内部后台），推送给运维和业务负责人。
和单纯机房动环告警的最大区别：动环只会告诉你电池有问题；AIOps 可以告诉你：这块电池出事之后，阿里云上哪些业务会受影响、业务优先级多高，指导你优先抢修高风险资产。
落地收益
：隐性供电隐患提前识别，同时完成
基础设施隐患到云上业务影响的预判
。
案例 3：机房专线割接变更，AIOps 自动校验阿里云侧是否异常
背景
：机房经常做专线扩容、交换机割接检修，变更人员只在机房工单系统登记，阿里云侧没有记录。经常出现割接后，云上出现抖动，过很久才发现是割接引发。
AIOps 实操方案
1. 机房变更工单推送到 AIOps，录入变更时间窗口、涉及专线/机柜；
2. 变更开始后，AIOps 自动订阅该专线对应的阿里云指标：专线带宽、丢包、云上应用错误率；
3. 变更窗口期内，如果阿里云指标出现异常，AIOps 自动打上【变更关联异常】标签，优先推送给变更负责人；
4. 变更结束，自动生成变更校验报告。以变更期间云上业务指标是否平稳，作为变更是否成功的依据。
这个能力解决了跨域变更的灰度校验，区分 “业务自发故障” 和 “机房改造引发的云上故障”。
阿里云侧对接的实操细节
这里给出可直接落地的接入方式，不是空谈架构：
1. 告警接入
：阿里云云监控、ARMS 支持 Webhook，直接配置回调地址到 AIOps 事件接收接口；
2. 指标与资产同
步
：调用阿里云 OpenAPI（云监控 OpenAPI、资产中心 OpenAPI），定时拉取 ECS、RDS、SLB、云连接、专线资产和指标；建议用 RAM 子账号，最小权限；
3. 日志接入
：SLS 配置投递（投递到 Kafka），AIOps 消费 Kafka 日志流，避免直接高频率拉 SLS 接口限流；
4. 权限规范
：RAM 子账号只开放只读观测权限，AIOps
默认不开放云上资源操作权限
，根因结论只做建议，不自动执行云上自愈，保障安全；
5. 机房侧对接：
动环设备优先 SNMP；新一点动环平台支持 HTTP WebService 接口；老款只能 Modbus 的，用边缘网关做协议转换后再输出标准化指标给 AIOps。
重点
：老机房大量传统动环没有开放 API，是对接最大卡点，优先用边缘网关做协议标准化，不要硬改动环主机。
落地路线建议（循序渐进，避免项目难产）
阶段 1（0-1.5 个月）：打通接入+资产映射
先把阿里云告警 Webhook、机房动环告警接入 AIOps；梳理专线、物理设备、云上业务的依赖拓扑表，完善标签。
这个阶段目标：告警统一汇聚，资产关系可查。
阶段 2（1.5-3 个月）：告警降噪、跨域聚类
做告警相似度聚类、抑制，同一故障窗口内区分根告警和衍生告警，先解决告警轰炸，团队快速拿到体感收益。
阶段 3（3-6 个月）：跨域根因推理、变更关联校验
在拓扑稳定后，上线跨域 RCA，优先打磨【机房基础设施 → 云上网络】这类高频故障场景。
阶段 4（长期）：容量联合预测、SLA 统一统计
比如机房带宽、专线容量预测，联动阿里云业务流量趋势，做统一容量规划。
总结
很多人对 AIOps 有两个极端理解：要么认为 AIOps 就是云上链路大模型 RCA；要么认为 AIOps 只是机房摄像头 CV 巡检。
在大量政企、制造业、中型互联网的混合架构里，AIOps 更务实的定位，是
跨域观测融合平台
：
1. 不替代阿里云原生监控，不淘汰跑了很多年的机房动环；
2. 把云侧、本地机房两套运维语言打通，预判基础设施故障对业务的影响；
3. 故障发生时，帮运维判断：是阿里云业务本身问题，还是底层机房供电、制冷、专线带来的连锁故障；
4. 统一事件、统一工单、统一复盘，解决两套运维体系 “各管一段” 的痛点。
混合云、云+自建 IDC 的架构还非常普遍，这种
跨域 AIOps，往往比纯云上 RCA 更容易做出别人没有的差异化价值。
