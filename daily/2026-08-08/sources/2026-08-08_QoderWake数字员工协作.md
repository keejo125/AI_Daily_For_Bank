最近，AI 网关团队多了一位新同学。它叫“AI 网关高手”，没有工位，常驻钉钉，可以被拉进项目群，也可以接收单聊。有人让它查产品配置，有人把问题截图发给它，也有人直接让它创建需求、流转缺陷或者去测试环境检查实例。数字员工上岗一周，它进入了 26 个群聊，收到 28 个私聊，累计回复超过 500 条消息。
我们做它，不是因为团队缺少一个写代码的工具。Qoder、Codex 这样的桌面 Agent 已经让个人研发效率提高了很多。我们想解决的是另一件事：当一个项目需要多人共同推进时，怎么减少信息转述、状态跟进和跨系统操作带来的沟通摩擦。
0 背景：个人效率提升后，团队协作成为新的瓶颈
过去一段时间，我们一直在推动建设 AI 网关项目的 Harness 工程，也总结了一套实践经验。桌面 Agent 已经能够帮助研发快速完成绝大部分代码开发工作。
但对于一个项目来说，个人写代码只是研发工作的一小部分。围绕项目推进，还有大量由 PD、研发、测试、交付、架构师等角色共同完成的工作。这些工作散落在群聊、文档、研发平台和实际环境中，需要不断补充信息、查询状态、执行操作并跟进结果。
以项目工作项管理为例，一条需求需要在Aone协作平台（阿里云内部代码协作平台）进行多次流转：架构师从客户和项目现场收集需求，补齐业务背景、场景、版本和期望交付时间，再把需求提交到 Aone。接下来，产品判断是否接受，研发评估技术方案和工作量，质量与测试评估验证范围，项目管理安排迭代和版本。需求进入开发后，还要经过自测、集成、集成测试、验收，最后才能发布。
一条Aone需求的生命周期：创建需求 → 待处理 → PD 已接受 → 技术已评估 → 质量已评估 → 已规划 → 开发测试中 → 开发自测完成 → 已集成 → 待集测 → 集成测试 → 已验收 → 已发布
AI Coding 大幅提升了开发阶段的效率，但需求评估、排期、状态流转、测试、验收和发布等环节并不会因此消失。即使编码、问题排查和变更准备的速度显著加快，单个环节的提效也未必能转化为版本迭代整体周期的缩短。
随着项目规模扩大，需求、缺陷、环境和协作群越来越多，原来靠人补信息、改状态、找负责人和转述结果的方式开始吃力。我们现阶段遇到的新瓶颈，不是缺少一个更强的个人工具，而是个人工作台里的项目能力还没有进入团队共同参与的协作流程。
数字员工帮助协作提效
“AI 网关高手”的目标从一开始就不是替研发多写几段代码，而是让项目能力直接出现在协作发生的地方。上线后的工作主要集中在下面四类场景。
工作项管理：把人工催办变成持续推进
在一个 Aone 工作项的生命周期中，技术判断和排期决策仍然由对应负责人完成。这些操作简单但重复度高，一旦规模大，AI 网关高手承担的是信息整理、查重、字段补齐、状态查询、标准流转和通知提醒，让工作项能够带着完整信息交给下一位参与者。
它能够根据客户问题整理材料，补齐项目空间、版本和归属等字段，一次性创建 6 条 OpenTrek AI 网关缺陷，并根据具体内容指派给合适的研发同学，随后单聊提醒验证负责人回归。
他还能够批量处理 40 条需求的状态流转，并将状态、版本、负责人和备注统一写回表格，原本需要逐条核对和录入的工作一次完成。
客户答疑：不是多一个答疑机器人，而是少一次人工转述
售前阶段：协助架构师进行商品 code 规格澄清
交付阶段：协助现场交付同学排查客户现场的交付问题
售后阶段：协助技术支持同学处理客户反馈的现场问题
由于项目的特性，AI 网关的不同用户分散在售前、交付、运维和技术支持等不同环节，问题也分散在多个项目群和单聊中。过去，前线同学经常要通过共享屏幕或截图把现场信息转给研发，研发再使用自己的桌面 Agent分析，最后把结果带回群聊。
AI 网关高手可以直接进入这些会话。群里的人通过文字、截图或语音提供信息，它基于项目文档、代码、部署基线和历史经验回答；需要查询实际状态时，再进入对应系统检查，并把结果返回原会话。前线不必先找到一位研发充当“转接员”，研发也不必在个人终端和支持群之间反复搬运信息。
环境排查：让查询、操作和结果回到同一个群里
项目有时候同一套测试环境里可能有多个团队共享资源。出现异常后，日志、资源状态、执行结果和阶段性结论都需要及时同步给群里的参与者。过去，这些信息通常留在研发个人的终端中，再由研发整理后转述到群里，信息同步不及时，不准确。
AI网关高手可以直接进入群聊，环境问题的排查信息直接在群聊公开共享，排查过程不再被切成“群里提问—研发登录—复制结果—回群解释”的多段流程。
群聊上下文整理：让参与者快速接上讨论
项目群里的信息往往分散在多人、多条消息中。后来加入或中途离开的参与者想继续讨论，通常需要翻阅聊天记录，或者请其他人重新复述背景。
AI 网关高手可以直接读取当前群聊中的已有消息，识别参与者、讨论主题、已经形成的结论和待确认事项；需要追溯更早内容时，再按时间、关键词或发送者查找历史消息。它把整理结果返回原群，参与者可以在同一上下文上继续提问、补充和纠正。
它处理的不是某一条孤立消息，而是把多人留下的零散信息组织成共同背景。后续协作可以直接从当前进展开始，不必每次重新补齐上下文。
以上这四类场景并不孤立，他们的共同点是：任务从钉钉会话发起，需要结合项目知识、群聊上下文或真实系统完成处理，再带着结果回到原会话继续协作。这意味着，我们需要的不是一个只负责收发消息的机器人，而是一个能够拥有项目经验，能够长期参与项目协作的数字员工。
AI 网关高手：让数字员工借助 IM 进行项目协作
我们的思路不是把代码仓库分发给所有人，也不是重新为每个角色建设一套知识库，而是让项目 Agent 继续运行在受控的仓库与工程环境中，再为它提供一个真实、独立、可管理的数字员工身份。
具体来说，我们申请了一个名为“AI 网关高手”的数字员工账号，将它接入钉钉并绑定 QoderWake。“AI 网关高手”服务的也不只是研发人员。产品、项目管理、测试、运维和交付人员都可以通过同一个入口使用项目已经沉淀的知识和能力，而不必直接接触代码仓库和工程环境。
对团队成员来说，“AI 网关高手”是一名可以单聊、也可以在群里被 @ 的数字同事。对系统来说，它是一个拥有独立账号、独立权限和完整操作记录的执行主体。

数字员工不只是名称，而是一套完整的工作身份
数字员工是一个真实的员工账号，拥有自己的内网权限，申请下来后需要用这个账号申请必要的权限。QoderWake 本身还支持接入钉钉机器人，机器人的申请比数字员工更简单，还不需要做权限管理，直接用自己的账号绑定权限更方便，为什么我们还要使用数字员工？
它解决了执行身份问题。Agent 查询或操作内网研发平台时，使用的是数字员工自己的权限角色，而不是某位研发同学的账号或凭证。人类员工的操作记录与数字员工的操作记录天然分离，查看平台日志或事项历史时，可以一眼判断某次操作由谁发起。
这种设计也让权限治理更加直接。团队可以围绕“AI 网关高手”单独申请、调整和回收权限，根据任务范围配置可访问的平台和可执行的动作，并对它的操作进行统一审计。数字员工因此不再是 Agent 的昵称，而是 Agent 在组织内真实工作的身份载体。
面向 IM 的 Harness 工程
要让这些协作场景真正发生，不能只把 QoderWake 的回复转发到钉钉群里。QoderWake 已经提供了原生的 IM 渠道支持，但在实际投入时，QoderWake 的原生 IM 渠道功能还不完全满足我们的需求。
桌面上的操作者、仓库和会话相对固定，IM 中的群和人员却随时在变化。数字员工可能突然被拉进一个新群，也可能在单聊中收到任务；它还要区分不同会话的权限，接住多人讨论形成的上下文，处理截图、文件和语音。我们把负责这些工作的桥接程序称为面向 IM 的 Harness。
作为临时方案，我们进行了面向 IM 的 Harness 工程扩展。在钉钉和 QoderWake 之间再补一层桥接层，这层桥接让 AI 网关高手有了七种更接近“同事”的工作方式：
被拉进新群，就能直接开始工作：
新群和新单聊出现后，桥接程序会自动接入，不同会话并行处理，不用提前逐个登记。像把一位同事拉进群，不用先找管理员配置机器人。
不是每个群都能直接操作项目：
白名单会话可以查询和操作项目系统；不在白名单里的会话只能答疑。它可以去更多群回答问题，但不会在陌生群里改需求、查环境或发通知。
任务处理到哪，原消息上就能看到：
进入等待的消息上贴“排队中”，处理时贴上“思考中”，完成回复上贴“已完成”，记录知识贴上“已记录”，意外中断贴上“已中止”，把处理结果留在原对话里。不用追着问“收到没有”“做完了吗”。
你说“看上面”，他知道“上面”是什么：
群里有人 @ 它时，桥接层会把必要的历史消息和引用关系一起交给 QoderWake，并隔离不同会话的上下文。用户感知：不用重新复制前情，也不用把多人讨论整理成一段完整 Prompt。
事情做完，直接去找下一位同事：
创建或流转完工作项后，它可以主动私聊负责人，也可以回到群里 @ 相关人员继续跟进。处理结果会继续送到该接手的人手里，不会停在发起人的对话框里。

使用 DWS Skill 可以将复杂操作过程沉淀为钉钉文档，并把文档链接发到群聊中。
我们也把这些实际需求反馈给了 QoderWake 团队，推动相关能力进入后续版本演进。QoderWake 团队对真实场景的反馈响应很快，2 天之内就补齐了相关的能力，并且在 2 个小时的会议交流中，发现双方有很多共同的想法，预计在下一周，我们就会把相关的“临时桥接”方案去除，改用 QoderWake 原生的“唤醒”能力，并验证多 Waker 挂载和 router 任务路由能力，将更多的精力放在业务的 Harness 工程上。我们相信专业的事情交给专业的人，会让 AI 网关高手变得更强。
完成数字员工账号申请并接入钉钉，只是让它拥有了进入团队协作现场的身份和入口。要让它真正理解 AI 网关并参与项目工作，还需要为它提供代码仓库、专业 Skill、项目 Harness 工程和知识库。
我们将 AI 网关相关的代码仓库直接提供给 QoderWake。数字员工看到的不只是一份静态代码，还包括仓库内部持续维护的 AGENTS.md、开发指南、设计文档、事实源索引、验证脚本，以及大量由项目自行管理的领域 Skill。这些内容共同构成了 AI 网关自己的 Harness 工程，让数字员工能够理解项目结构、产品形态、研发规范、操作边界和验证要求。

这些通用 Skill 让数字员工能够连接研发平台、专有云环境和钉钉，但“会使用工具”并不等于“理解项目”。真正让这些工具围绕 AI 网关正确运转的，是代码仓库内由团队持续维护的 Harness 工程。
例如，当数字员工收到一个环境问题时，xterm-env 告诉它如何查询环境，仓库内的指南和领域 Skill 则告诉它应该检查哪些组件、如何区分不同交付形态，以及怎样判断结果是否符合预期。当它处理一条需求或缺陷时，a1 Skill 提供平台操作能力，项目 Harness 则定义信息准入、状态流转、负责人识别和完成标准。只有两者结合，它才能从“调用工具”进一步走向“按照团队的方式完成工作”。
这也是我们在 AI 网关项目中持续建设 Harness 工程的原因。Harness 工程不只服务于 Qoder、Codex 等桌面端 Agent，同样也是让数字员工变得聪明、可靠的关键。桌面 Agent 和数字员工虽然工作入口不同，但共享同一套代码事实、项目知识、工程规则和质量标准。仓库中的内部文档越完整，自管理 Skill 越丰富，验证和流程约束越清晰，数字员工能够独立承担的工作就越复杂。
除此之外，我们还使用 QoderWake 内置的知识库系统，补充不适合直接放入代码仓库的业务材料和团队知识，例如产品介绍、常见问题、交付经验、历史方案与操作手册。
这几部分共同构成了数字员工的能力基础：
代码仓库为它提供真实、持续更新的项目上下文；
通用 Skill 决定它能够连接和操作哪些系统；
仓库自管理 Skill 和内部文档告诉它如何按照项目规则完成工作；
Harness 工程为任务执行提供流程、边界和质量保障；
知识库补充代码仓库之外的业务背景与团队经验。
因此，招募一位数字员工并不是简单地为 Agent 接入一个钉钉账号，也不只是安装几个 Skill。真正让它理解项目、融入团队并持续成长的，是代码仓库、专业工具、知识体系和 Harness 工程的共同建设。
总结与展望
AI 网关高手并不是要替代桌面 Agent，而是要把已经在个人终端中验证过的 AI 能力带进团队协作。项目研发不会在一个人的终端里结束，需求、问题和处理结果还要经过产品、研发、测试、运维和交付等多个角色共同推进。我们以 QoderWake 作为 Agent 载体，通过独立的数字员工账号提供组织身份，再由面向 IM 的 Harness 承接会话、权限、上下文和后续通知，让项目能力真正进入团队日常协作发生的地方。
现阶段，我们没有把缺陷自动修复和需求直接开发作为 AI 网关高手的第一优先级，并不意味着数字员工的能力会止步于答疑、排查和流程协同。我们的选择更多来自对团队当前痛点和工程稳定性的判断：先解决信息转述、状态跟进和跨系统操作这些最影响协作效率的问题；对于代码修改，则继续交由 Qoder、Codex 等桌面端研发智能体完成，由研发人员参与过程并把控最终质量。
随着 AI 网关 Harness 工程持续迭代，这一边界也会逐步向前推进。通过补齐需求准入 Skill、需求澄清 Skill、自动化 Verify 能力以及多任务并发处理能力，我们希望为研发任务建立更完整的输入标准、过程门禁和结果验证机制。在此基础上，下一阶段我们计划将 AI 网关高手“晋升”为数字员工 Leader：它不再只是亲自处理协作任务，还能够拆解、分派和跟进研发工作，带领更多专业研发智能体完成需求开发与缺陷修复，并将进展和结果持续带回团队协作现场。

对接钉钉渠道
创建完了 waker，还需要让它连接到数字员工的钉钉账号。QoderWake 原生支持连接钉钉，需要在渠道管理中添加钉钉用户，QoderWake 会自动安装 DWS 并跳转到钉钉登录页进行登录认证。
添加完钉钉渠道后，就可以到会话管理中添加配对会话，QoderWake 会建立钉钉会话和 Waker 的绑定关系，统一管理钉钉消息和数字员工的交互。
添加配对会话后，就可以在钉钉中和数字员工进行对话了。
即使不使用我们自制的桥接层，AI 网关高手还是能够接入钉钉进行工作，而且 QoderWake 在并行处理上相对桥接层方案做了优化，在这方面有更好的体验。但它会失去自动接入新会话、主动提醒和多模态消息收发等能力，缺少了一些真人感。
至于群聊历史补充、状态标记在 QoderWake 灰度版本中也已经支持，并且还会新增 resume、插话、btw（随时查询任务状态）等能力，我们也将在下周对接 QoderWake 内测版本，提升在同一群聊中并行处理多个 @ 的能力。至于桥接层如何做到这些事，我们先留一个彩蛋，后续再单独写一篇文章展开
