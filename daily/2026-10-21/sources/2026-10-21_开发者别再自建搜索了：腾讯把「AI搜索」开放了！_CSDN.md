# 开发者别再自建搜索了：腾讯把「AI搜索」开放了！

来源：CSDN
原文链接：https://mp.weixin.qq.com/s/5Ko_DD5X1OHGO6jZKg2qXA

做 AI 应用的人，大概都经历过这几个瞬间。
当你给企业知识库接了联网检索，用户问一个行业政策，模型一本正经地引了一段"新规"。你去查原文，那是个两年前的旧文件，出处是一个没人听说过的营销号。模型对信源是没有防御机制的：你喂给它十篇互相矛盾的水文，它就给你编出一个看起来最通顺、但谁也没说过的"事实"。
再比如给 Agent 装了个联网工具，让它查个版本发布说明，它先搜回来 20 个网页，一半是过期教程，一半是 SEO 洗稿，然后吭哧吭哧读了半天，回答还是没答到点子上。让 AI 帮忙查资料，查完一大段回答，才发现版本对不上，或者根本找不到原文。
这几件事看起来不相关，其实是同一个问题：大模型从 "能对话" 走到 "能办事" 之后，
它需要的不再是一个网页搜索框，而是一套能直接喂给模型的、干净的、实时的、带权威度标注的事实。
这意味着准确、权威、时效且高速的搜索将扮演重要的角色。
10月20日，
元宝搜索
全面升级，正式
以 API 形式在腾讯云正式对外开放
，
面向个人开发者和企业客户，提供即开即用的搜索能力。
有趣的是，腾讯并没有把这次开放当作一个简单的“功能上新”，而是把它定义为一次“能力解耦”。这意味着，元宝搜索不再是元宝 App 里的一个隐藏功能，而是一套可以被任何应用、任何场景灵活调用的独立服务。
为什么幻觉成了行业公敌
为什么大模型时代，搜索能力突然变得如此重要？
要回答这个问题，得先看清大模型的一个本质特征
：
大模型的生成机制本质上是一个概率游戏
，
给定上文，预测下一个最可能出现的词。它被训练成“给出一个看起来合理的答案”，而不是“给出一个事实上正确的答案”。当模型的知识储备里没有某个具体事实时，它不会说“我不知道”，它会基于语言模式生成一个看起来合理的替代品。
腾讯云副总裁、元宝搜索研发负责人
马晋
对此表示：
，
把大模型的短板总结成三个 "阿喀琉斯之踵"：
幻觉、时效性、行业知识盲区
。它会一本正经地引用不存在的法条和人名，对训练截止日之后发生的新闻、比分、政策一无所知，更读不懂千行百业的 "黑话" 和企业内部知识。
传统解法是微调、RAG、提示词约束，但所有这些方法都有一个共同前提：你得先把正确的信息喂给它。而搜索能力，恰恰是解决这个动作的实时性和覆盖面的关键。
这就是搜索在大模型时代角色突变的根本原因。过去搜索是 "帮用户找网页"，现在搜索是 "帮模型找事实"。前者对召回率的要求是 "尽量多"，后者对准确率的要求是 "不能错"。
具体来看，传统搜索面临以下几个痛点：
一是数据质量差。
传统搜索引擎充斥
着大量 SEO 农场、营销号、洗稿账号和过期页面。大模型对信源是没有防御机制的
。
它不会因为一篇文章来自一个没人听说过的自媒体就自动降低采信度，它会把上下文里所有内容一视同仁地当作事实来推理。你喂给它十篇互相矛盾的水文，它就给你编出一个看起来最通顺、但谁也没说过的 "事实"。
二是工程成本极高
，传统搜索的工程链路是为“人”设计的，从爬虫抓取、去重、排序到前端展示，每一步都依赖大量人工规则和运营经验。而大模型的搜索则要求全链路自动化、实时化，从索引构建、语义理解到结果生成，每一步都需要重新设计。而企业要想自建一套这样的系统，不仅要投入巨大的算力资源，还要组建专门的算法团队持续调优，这个门槛对绝大多数企业来说，几乎是不可逾越的。
三是语义理解能力不足
。传统搜索基于关键词匹配，用户输入“苹果公司的创始人是谁”，它返回的是包含这些关键词的网页列表。而大模型搜索要求理解“苹果”是指公司而非水果，“创始人”是人物而非职位，这背后涉及实体识别、意图消解、指代消解等一系列复杂的语义理解任务。
这种长尾、复杂的语义，关键词匹配召不回、召不准；而模型拿不到精准召回的素材，只能退回到"凭记忆编"的老路。
四是内容存在孤岛
，例如企业内部的知识库、数据库、私有文档，这些高价值信息往往沉淀在OA系统、CRM、ERP或本地文件服务器里，传统搜索引擎根本爬不到，更谈不上索引和排序。大模型即便再聪明，面对这些“看不见”的数据，也只能基于训练时的公开语料进行推测，无法真正触达企业内部的真实数据和业务逻辑。这就导致两个问题：一是大模型的回答往往是“泛泛而谈”，缺乏针对企业具体业务场景的深度洞察；二是即便企业内部有大量高质量数据，也无法被有效利用，形成数据沉睡。
综合起来看，这个答案就很明显了。对于开发者和企业而言，
他们需要的是一个能直接接入内部数据源、理解业务语义、并且能对结果负责的搜索基础设施，而不是一个只能依赖公开网页、无法穿透企业数据孤岛的通用引擎。
换言之，传统搜索解决的是“找得到”，而企业真正需要的是“答得准”。因此，企业级搜索的下一步
需要建立优质内容的基础上，增强垂直领域知识，
两者叠加，才能真正实现从“搜得到”到“答得准”的跨越
。
这也进一步回答了元宝搜索的升级路径。
元宝搜索做了什么？

认知：让搜索"自进化"，和 Agent 互相投喂
元宝搜索在搜索行业里很早引入了
RSI 式的数据飞轮
：即自动挖掘用户不满意的搜索结果，由智能体标注样本，增量训练模型，形成"发现问题 → 增训 → 效果提升"的闭环自进化。用马晋的说法，这是"数据飞轮驱动的自进化闭环。
同时搜索和智能体之间做
双向协同
：Agent 把 query 拆得更适合检索，搜索把权威性等级、发布时间等信号回传给 Agent，两边互相投喂特征、共同抬高最终答案的质量。
算法：三阶段排序训练 + Gist Token 压缩
排序侧走的是"Label 模型打标 → Teacher 大模型学复杂偏好 → 蒸馏到 Student 小模型上线"的
三阶段训练范式
，兼顾效果和在线成本。
最值得一提的是
Gist Token 压缩技术
：这是一项堪称“降本增效”的杀手锏。它能把一篇长达几 K token 的网页全文，直接压缩进约 100 个 Gist token 中。在推理时通过复用 KV Cache，在保证细粒度辨识能力的同时，大幅降低了推理延迟和 Token 成本。马晋透露，这大约能节约 30% 的在线推理成本。
架构：倒排 + 向量融合索引，检索进入 10ms 时代
架构方面，
业界首创了
倒排与向量索引的融合
（支持精确检索+近似检索），召回率达到 94% 以上，底层检索耗时压到了 10ms 以下。单机装载容量超过 10 亿向量，支撑起了 1500 亿以上的向量索引规模
，
推理框架做了存算分离、投机解码、算子融合等一揽子优化，整体端到端最快 300 多毫秒返回。
马
晋
坦言，搜索永远面临“成本、耗时和效果”的平衡（不可能三角），而元宝搜索的解法是用更聪明的架构去逼近这个极限。
内容：生态信源 + 从源头挡谣言
内容方面，
从源头严控质量
。
一方面深度打通腾讯内外核心资源，比如腾讯新闻、腾讯体育、腾讯医典
，以及地图、视频、音乐、浏览器、FiT 等内部生态，同时接入京东、携程、美团、非常准等头部合作方；另一方面用大模型做多源交叉验证和低质内容过滤，权威信源优先。
据马晋介绍："从信源的原创性、可信度，到内容的真实性、丰富度、专业度，都有多维度的判断，最终聚合起来判断内容来源的可信程度和内容价值。"对 UGC 内容也"不是一刀切，要按意图分场景，政策、新闻、医疗法规这类权威性要求高的，肯定是政府官网、企业官网"。
旗舰版甚至直接返回"结果权威度等级"字段，开发者可以据此写规则：低质结果不喂给模型。
合起来看，这次升级的完整图景就清晰了

为全行业的 AI 产品提供即开即用、可信可靠的内容检索基座。

全程不烧心
账号在腾讯云完成实名认证并开通服务后，系统会自动分配密钥。整个过程最直观的感受是：没有复杂的鉴权配置，没有冗长的SDK文档，三种接入方式（API、Skill、MCP）按需选择，完全对应不同开发阶段的需求。
直接调 API：后端开发者的最爱
我
们首先
用本地脚本读取 SecretId 和 SecretKey，完成签名后调用 SearchPro。查 Python 发布说明时，传入的参数是：
{
"Query": "Python 3.15.0 release date major new features",
"Site": "python.org",
"Cnt": 10,
"Mode": 0
}
Query 填要查的内容，Site 填希望限定的域名。这条请求返回 HTTP 200，共 10 条结果，耗时 0.397 秒。
调用、保存结果和日志都放在自己的程序里，后面要加引用展示或其他处理，也可以接着写。签名部分可以交给 SDK 或封装脚本。
Agent 开发者：用 Skill 极简接入
如果你已经在使用支持 Skill 的 Agent 客户端，
在 SkillHub 下载元宝搜索 v1.0.4
。
解压后，包里有 SKILL.md、配置说明和 Python 搜索脚本。技能说明写好了何时搜索、怎样传参；脚本负责请求接口，并把结果整理成 Markdown。
这里有一处要分清：Skill 用的是元宝搜索“服务 API Key”，不是前面的 SecretId／SecretKey。 按说明将 Key 配到 TENCENTCLOUD_WSA_APIKEY 环境变量里，脚本就能读取。
为了看清楚它的输出，我直接在技能目录执行了官方脚本：
python scripts/websearch.py --query="Python 3.15.0 release date major new features" --site="python.org" --cnt=10 --mode=0
结果是 10 条 Markdown 搜索结果，带着标题、链接和摘要。进程总耗时约 0.648 秒，其中包含 Python 启动、网络请求和格式化时间。
拿到这种格式，后面整理笔记或交给 Agent 阅读都比较方便。用支持该技能的客户端安装时，按页面和包内说明配置即可；我这次验证的是脚本执行，Agent 自动触发的体验另算。
MCP 客户端：开箱即用的远程工具
在腾讯云 MCP 广场获取元宝搜索的服务地址，配置好同一个 API Key 即可。
我们
用本地协议客户端连接后，在工具列表里看到了 SearchPro。用它查询同一份 Python 发布说明，成功返回 10 条结果，这次工具调用耗时约 0.360 秒，初始化和工具发现的时间另算
。
三种入口都接通以后，就可以按自己已有的工具选择了。
整个接入过程不超过5分钟，简直是开发者的福音了。

Python 3.15 做一次硬核选题
为了检验元宝搜索在信息收集上的可靠性，我
们
设计了一次真实的选题测试：
Python 3.15 发布后，开发者在升级前需要核对哪些条件？
第一条请求，我
们
直接把选题需求发了过去：
“Python 3.15 正式发布，有哪些适合开发者关注的变化？核对发布日期、JIT 的适用条件、自由线程的限制，查找官方资料。”
返回的 10 条结果里，前几条是发布介绍，第 7 条出现 Python 官方发布页。先看这一轮，编码变化、导入机制、JIT 和自由线程几个方向就都有了线索。
接着单独查发布说明，并加上 Site=python.org。首条标题就是 “Python Release Python 3.15.0”。
这时选题也收窄了：重点写升级前的检查项。
接下来就分别查 JIT 和自由线程
，把容易说含糊的地方弄清楚。先看 JIT 的提速数字。
这一条限定了 docs.python.org。结果里找到了 3.15 的更新说明，也出现了不同语言、不同文档分支的页面。我选了对应版本，打开原文看具体条件。
文档仍把 JIT 标为实验性功能。常见的 7%—8% 这个数字，指的是 x86-64 Linux 上特定基准套件的几何平均提升；换一种工作负载，可能提速更多，也可能变慢。
再看自由线程和扩展兼容。
另一条查询返回了自由线程的 C API 扩展支持和使用说明。原文把解释器构建、扩展模块支持，以及运行时的 GIL 状态分开讲。仅仅升到某个 Python 版本，还不能据此判断整个项目已经适配。
查到这里，文章里可以给读者的检查项就具体了：用的是什么构建，依赖里有哪些扩展，运行时状态又是什么。每一项都有文档可以继续查。
发布页的链接也顺手处理了一下。查询首条给的是 downloads/latest，这种入口以后可能指向别的版本。我把文章引用固定到 3.15.0 的发布页，后面回查更方便。
一轮查完，提纲可以这样写：从发布消息切入，解释默认编码和导入机制的变化，再写 JIT 的条件、自由线程的扩展兼容问题，最后整理升级前的检查项。
这个选题用了 4 次 API 请求，各返回 10 条结果。耗时依次约为 0.720、0.397、0.483、0.503 秒，中位数约 0.493 秒。这是请求到完整收到响应的时间，打开网页和人工核对的时间另算。
从开始查询到确定提纲，整个过程大约用了二十分钟。其中大部分时间花在阅读文档原文上，
真正用于搜索的时间并不长。
如果把这个过程拆开来看，搜索只是第一步，后续的阅读、比对和取舍才是决定文章质量的关键。
当然，最终选题还是要以人作为评判标准，但一个明显的变化是，从"先查什么"到"怎么查"的决策，已经可以交给工具完成，而人的精力可以更集中在"查到的内容意味着什么"上。
元宝搜索开放！开发者："轮子"不用再造了！
把这次升级放到更长的时间线里看，腾讯在搜索这件事上的角色，其实悄悄发生了一次转变。过去，元宝搜索是元宝 App 里的一个功能，用户打开 App、问一个问题、得到一个带引用的答案。它服务的对象是 C 端用户，是腾讯自己产品的体验细节。
现在，它被从 App 里拆了出来，变成腾讯云上的一个 API。调用它的，可以是 WorkBuddy、ima、腾讯视频这些自家兄弟，也可以是外面任何一家做大模型、做智能座舱、做办公协同、做金融投研、做在线教育的团队。
马晋对此表示：“我们并不去做搜索独立的入口，这个入口的工作交给各个 App 来完成。我们会在这些产品背后提供更优质、更可信的搜索信源。”
对开发者而言，这意味着“轮子不用再造了”。
你不需要重复检索，不需要去和 SEO 农场斗智斗勇。腾讯把在 WorkBuddy、ima、腾讯金融科技验证过的那套基座，打包成了几行代码就能调用的接口。
