# Agent Sandbox 重磅发布：让智能体获得一个即时、可控的执行世界

来源：阿里云基础设施
原文链接：https://mp.weixin.qq.com/s/6FPNlsqdcPYUsQNbFjfJLQ

本文整理自 2026 云栖大会「构建 Agent Infra，Agent Sandbox 重磅发布与技术架构揭秘」分论坛，阿里云智能集团资深产品专家杨秋弟、资深技术专家杨皓然《阿里云智能体沙箱 Agent Sandbox 重磅发布与技术解析》主题演讲。过去，AI 技术的进步主要围绕模型展开：预训练扩展模型能力，后训练扩展经验，Test-time 进一步扩展思考。随着 Agent 开始规划任务、调用工具、进入执行环境，并将结果反馈给模型，模型能力、环境反馈与应用执行逐渐形成新的数据闭环。AI 的竞争也由模型能否“想得到”，延伸到 Agent 能否在真实环境中把任务做完整。这意味着，模型之外还需要一套能够承接行动的执行基础设施。一、Agent 的运行方式，正在改变计算环境的基本假设传统程序通常按照预定义流程执行，负载相对可预测，资源也可以根据容量提前预置。Agent 则在运行时动态决策：下一步做什么、调用哪一种工具、需要多少资源，往往只有执行到相应阶段才能确定。不同任务的运行特征也可能相差很大。一次代码或文件工具调用可能只持续很短时间，浏览器任务可能运行数分钟，长时 Agent 则需要跨越多轮交互和多个步骤保存状态，并支持暂停、恢复与分支。由此带来的变化同时作用于四个方面：资源需求形成于运行时，需要随任务弹性供给；执行内容动态生成，权限与网络边界必须受控；任务跨步骤推进，需要保留和恢复状态；资源用量动态变化，需要按照实际占用优化成本。任何一项缺失，都会在规模化运行时变成系统性风险。Agent 所需要的，不是把传统计算环境直接平移过来，而是让资源、安全、状态与成本，随任务动态适配。二、为每个 Agent，即时创造一个可控的世界阿里云智能体沙箱 Agent Sandbox （以下简称 Agent Sandbox）——为智能而生的新算力形态，为每个 Agent 即时创造一个可控的世界。“即时”意味着任务到来时能够快速创建环境并弹性供给资源；“可控”意味着身份、权限、网络、数据和执行边界清晰受控；“世界”则意味着沙箱不只是一个进程，而是包含运行时、文件、网络、状态和可观测能力的完整执行环境。围绕这一目标，Agent Sandbox 提供模板管理、沙箱管理、会话状态、安全隔离、文件卷管理、网络策略和可观测能力，覆盖环境构建、任务执行、状态保留与资源回收的完整链路。这项产品能力并不是从零开始构建。阿里云将 API-first、开箱即用的 FC Sandbox，与 Kubernetes 原生、面向规模化治理的 ACS Sandbox 深度融合，形成一个产品入口、统一技术底座与资源供给，并保留两种原生接入方式。面向 Agent 开发者，Developer API 原生兼容 E2B，开发者通过几行 SDK 即可执行代码、操作文件或浏览器，并将结果返回 Agent，无需直接管理底层基础设施。面向 AI Infra 和平台团队，Kubernetes API 允许通过声明 AgentSandbox 的期望状态自动交付沙箱，并将其纳入已有的资源管理、网络策略和安全治理体系。两种入口共享同一套运行时底座，使应用团队能够快速验证业务，也让平台团队能够继续沿用 Kubernetes 的管理方式完成规模化交付与治理。三、Agent 生产级运行：高性能、低成本、安全可信Agent 进入生产环境，首先要解决的是能否在明确边界内可靠执行。Agent Sandbox 将安全边界分为应用安全隔离和运行时安全隔离两层。应用安全隔离负责控制访问边界。每个 Agent 绑定独立身份，长期密钥不进入沙箱；入站请求需要认证，出站访问受网络策略约束，关键访问行为可以审计和追溯。运行时安全隔离负责守住执行边界，代码、工具和进程运行在 MicroVM 强隔离环境中；主容器采用 Non-root、只读根文件系统并禁止提权，VPC 与 NetworkPolicy 默认最小可达，临时盘和动态挂载在任务结束后回收。两层边界结合后，相邻任务之间以及任务与宿主环境之间不可见、不可越界。性能和成本则需要随负载类型分别优化。工具执行具有短周期、高频创建和突发流量等特点，关注启动延迟与创建吞吐；Long-running Agent 生命周期更长、状态依赖更强，运行中还可能存在较长的 I/O 等待，因此更关注暂停、恢复和状态持续保存；Agent RL/Eval 需要批量 rollout、reset、fork 和 replay，重点是高并发处理与大规模资源供给。针对这些负载，官方模板或自定义模板预热后，冷启动 P99 小于 180ms；沙箱实例资源池预热后，热启动 P99 小于 20ms；深休眠唤醒 P99 小于 600ms；沙箱创建吞吐达到 10 万次/分钟，单 Region 支持百万级 Sandbox。休眠期间可以释放计算资源并持续保存状态，从而减少长时任务等待阶段的计算资源占用。为了进一步平衡性能与成本，Agent Sandbox 提供经济型、通用型和性能型三档算力 QoS，并可在不改变 API 的情况下切换。经济型以成本优先，vCPU、内存和磁盘单价分别为 0.060 元/vCPU/小时、0.030 元/GiB/小时和 0.0021 元/GiB/小时；通用型面向生产级沙箱，三项单价分别为 0.078 元、0.039 元和 0.0021 元；性能型采用专属资源池刚性交付，三项单价分别为 0.120 元、0.060 元和 0.0021 元。产品采用秒级计费，不足 1 秒按 1 秒计算，每小时出账一次；磁盘费用只计算超出 15 GB 免费额度的部分，深休眠时仅收取磁盘费用。产品能力的极致表现，源于对底层链路的深度重构。要让上述能力在规模化运行中成立，Agent Sandbox需要同时解决两个问题：一是大规模并发下的快速就绪，二是任务执行过程中的安全可信。四、低延时要优化全链路，高吞吐要优化瓶颈环节一个沙箱从收到请求到就绪，要经过数据缓存、调度、MicroVM 或容器运行时、网络连接和初始化等环节。端到端延时等于关键路径上各环节耗时之和，而系统吞吐由整条链路中最窄的瓶颈决定。低延时与高吞吐是两类不同目标，却必须同时满足；任何一个环节吞吐不足，都可能在突发并发下成为整条链路的瓶颈。因此，Agent Sandbox 并不只追求 MicroVM 本身“启动得快”，而是把数据、资源、调度、计算和网络作为同一条链路优化。核心原则是：低延时需优化全链路，高吞吐需优化瓶颈环节。强化学习和评测场景中的镜像通常高度异构。典型镜像约为1GB至数GB，一次任务可能同时启动数千个来自不同镜像的沙箱。如果每次都从远端完整下载，既会拉长单次启动，也会形成回源风暴，使后端存储成为瓶颈。为此，在设计数据层时首先采用“只读基础镜像加单一活动 Diff”的模型。只读基础数据可以跨节点、跨实例共享，运行中的新增和修改写入增量层，并通过自动合并控制 Diff 层数，避免读取路径随版本增长。相同基础数据只需要保存一份，也使休眠等操作更加轻量。在此之上，节点本地缓存、CPFS区域共享高速文件存储和OSS对象存储形成Working-set Pyramid，让越热的数据越靠近计算。演讲援引业界论文和实际集群观察指出，沙箱启动及使用过程中真正读取的数据约占镜像的5%至10%，因此系统采用按需读取和热点填充，而不是搬运完整镜像。对可预测热点，可以提前Prewarm；节点间通过P2P复用已加载内容；缓存未命中时，则按用户或模板设置Miss Budget，并通过Admission、Throttle和Fast Fail等过载语义控制回源。整套机制可以归纳为三个词：数据去重、按需读取、回源可控。五、把可共享的重操作移出启动热路径数据就绪后，调度、MicroVM 创建和网络建连仍可能成为关键路径上的瓶颈。对应的优化遵循同一个原则：把耗时较长、可能成为瓶颈但可以共享的工作前移到请求到来之前，启动热路径只处理每个 Sandbox 独有的状态。数据就绪后，下一步进入资源调度。面对一批并发请求，调度采用批量处理、全内存决策和候选节点并行评分，一批请求进入后一次完成多个实例的放置，并复用计算结果。由此，实例调度延时 P99 小于 20ms，并支撑 10 万级/分钟的实例创建吞吐。MicroVM 启动则采用快照恢复。应用初始化提前完成并固化到快照中，多个 MicroVM 可以从同一份快照恢复；恢复时按页加载实际访问的数据，通过 Copy-on-Write 共享基础页，并结合 Trace 预取启动阶段的热点页。系统只需为每个实例重建时间、随机种子和网络连接等唯一状态。在 2c2g、热缓存、相同模板复用 Page Cache 的测试条件下，单机 50 并发的 MicroVM 启动 P95 为 134ms，单机启动吞吐达到 150 个/秒。此外，网络侧将共享转发面和 VPC 通道等较重资源提前池化，实例启动时仅创建或复用 TAP，再通过 eBPF 完成 Sandbox 与 VPC 身份的延迟绑定。启动过程由创建和配置整条网络链路，缩短为一次轻量的数据面绑定。端到端 VPC 建连延时由此控制在 10ms 以内，单节点网卡密度达到 4000。端到端测试进一步覆盖了镜像复用和高度异构两种情况。启动 500 个相同镜像的 Sandbox 实例时，共享镜像与缓存路径，P99 就绪延时为 500ms；启动 500 个不同 SWE-bench 镜像的 Sandbox 实例时，500 个独立 Working Set 并发就绪，P99 延时为 2.3 秒。后者更接近 SWE-bench、大规模强化学习和评测中的异构工作负载，也检验了系统在缓存压力和突发请求下的表现。六、安全不是一个隔离层，而是一条可信链快速启动只是沙箱进入生产环境的一部分。实例开始执行后，还必须回答另外几个问题：请求来自哪个 Agent，代表哪个用户或任务，被允许访问哪些资源，发生问题后能否完整追溯。MicroVM 可以限制不可信代码的执行边界，却不能单独完成对网络、身份、凭据和证据的约束。完整的安全能力需要让不可信代码连续通过运行、网络、身份、凭据与审计控制：运行时隔离限制执行范围，网络策略限制可达位置，身份机制确定请求主体，短期凭据限制权限，审计证据支撑追溯。每一次跨边界，都重新验证。这条可信链落实在 Agent Sandbox 的请求处理路径中，请求首先经过入站认证，沙箱内部生成的请求不能依靠自行声明的身份与凭据获得信任；进入可信数据面后，系统根据运行时上下文完成来源绑定，再执行网络地址、端口和角色等安全策略。真实凭据不进入沙箱，而是在请求进出沙箱时通过短期凭据代签或替换授权头完成授权，最终仍由目标服务执行授权判断。来源绑定、策略判定和授权结果被关联记录，并支持后续追溯、撤销和清理；运行时监控则负责容器逃逸检测和风险上报。由此，安全控制从执行隔离延伸到网络、身份、凭据与审计。每一次跨边界，都重新验证；沙箱行为必须可验证、可授权、可追溯。七、从快速接入到规模化生产Agent Sandbox 的生产实践覆盖了启动效率、资源成本、突发流量和迁移效率等不同目标。MiniMax 可在 10 秒内拉起 5000 个沙箱，整体 TCO 降低 25%；前程无忧面向数万次/分钟的突发流量完成刚性交付与弹性扩容，启动时间缩短 60%；某汽车客户在 1 天内通过 E2B Adapter 完成迁移，沙箱拉起时间约为 200ms。这些场景对应的并不是同一项孤立指标，而是 Agent 从开发验证走向生产运行时需要共同面对的问题：开发者需要低门槛接入，平台团队需要规模化治理，执行环境需要在异构并发下保持可预测，并让不可信代码的每一次行动都处于连续的安全控制之中。当模型开始持续进入真实环境、调用工具并完成任务，基础设施需要承接的也不再只是一次计算，而是一个可执行、可治理、可规模化的完整行动过程。模型决定 Agent 能想多远，Sandbox 决定它能走多远。
