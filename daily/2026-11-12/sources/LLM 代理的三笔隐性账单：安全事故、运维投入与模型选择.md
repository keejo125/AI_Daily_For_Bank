# LLM 代理的三笔隐性账单：安全事故、运维投入与模型选择

来源：阿里云云原生
原文链接：https://mp.weixin.qq.com/s/PuClVwke9fsuOU0Oi2L5tw

从 LiteLLM 2026 年的连环失守说起，聊聊 AI 应用入口的架构选择。现在开通阿里云 AI 网关智能路由，还可领取价值 200 元的 Credits 资源，直接抵扣智能路由消耗
（详见文末）
。
做大模型应用的团队，过去一年大概都经历过这样的演进：一开始只接一个模型，后来接了一组；为了统一管理 API Key、计量和限流，架起了一个 LLM 代理；模型越接越多之后，又冒出一个新问题——每次请求到底该让哪个模型处理。
这条演进路上，有三笔账很少有人提前算：安全事故的代价、自建自维护的投入、以及散落在应用代码里的模型选择逻辑。这三笔账，恰好都能从 LiteLLM 2026 年的经历里找到注脚。
01
半年两次投毒与密集高危 CVE：
架构位置带来的必然风险
Cloud Native
LiteLLM 是周下载量约 2300 万的开源 LLM 代理。2026 年 3 月和 10 月，它两度遭遇供应链投毒：攻击者或通过被污染的 CI 拿到发布 Token，或用盗来的开发者 OAuth Token 篡改发布工作流、从仿冒仓库构建——第二次里源码是干净的，有毒的只是构建产物，发布审批还被“正常”通过了。恶意代码利用 Python 的
.pth
启动钩子，不需要 import litellm 就会执行，专门查询代理数据库，导出组织里所有上游模型厂商的 API Key。
漏洞层面同样密集：预认证 SQL 注入（CVE-2026-42208，CVSS 9.8，公告发出 36 小时即出现在野利用）、MCP 测试端点命令执行（CVE-2026-42271，已入 CISA KEV）、MCP 认证绕过（CVE-2026-59822）、虚拟 Key 提权（CVE-2026-47101）等，多个为 CRITICAL 级。
单看每一起，都能归因为“某个账号被盗”“某段代码没写好”。放在一起，则是结构性问题：
自建 LLM 代理天然具备攻击者最想要的三个特征——钥匙集中
（所有厂商的 Key 汇总一处）；
位置敏感
（跑在生产集群、带着云角色、必须能出公网）；
扩展即进程
（Python 依赖和回调与代理同权限，进程能读的文件、环境变量、网络它都能用）。
前两条由业务需求决定，无法回避；爆炸半径则取决于第三条。因此关键问题不只是“会不会出事”，而是出事之后，恶意代码究竟能带走什么。
02
架构决定爆炸半径：
Wasm 沙箱+不可变发布
Cloud Native
这正是阿里云 AI 网关（与开源 Higress 同源）与 Python 系代理的分水岭。AI 网关数据面基于 Envoy（C++），AI 代理、鉴权、限流、内容安全等扩展能力以 Wasm 插件形式运行在内嵌虚拟机里。根本区别在于：
Python 依赖默认拥有进程的全部权限，Wasm 插件默认只有宿主明确开放的几项能力。
把投毒事件的恶意动作放进沙箱推演，逐条都会被拦下：
没有启动钩子
：
不存在“装上就执行”的机制，插件只有被显式引用才加载；
没有文件系统
：
云凭证、SSH 私钥、K8s Token 一个字节都读不到；
环境变量默认不可见
：
无法通过 env 窃取任何配置信息；
不支持 socket
：
外发请求只能经 Envoy 转发到已注册的服务，POST 到仿冒域名无路可走；
进程与内存隔离
：
起不了子进程，也读不到其他插件的内存。
沙箱之外还有三项配套机制：
加载校验
：
插件按“版本号 + sha256”锁定加载，校验和不符直接拒绝；能力拆分、最小授权；
密钥托管
：
企业版的 API Key 由 KMS 加密托管，配置里只留加密引用，不以明文出现在文件、环境变量或日志中；
不可变发布
：
官方插件采用“构建一次、评审快照、按 digest 晋升”的流程——制品绑定源码 commit 和输入哈希，正式发布只复制已评审的制品、从不重新构建，公共标签不可变、digest 不一致直接失败。
03
运维纪律的平台化承载：
Serverless 零门槛起步
Cloud Native
架构安全是底子，自建网关的安全最终还要落到运维纪律：镜像从哪拉、版本锁没锁、漏洞多快跟进、高峰容量留多少。一个容易被忽略的对照是：LiteLLM 官方提到，
使用其私有企业镜像仓库的客户没有受 10 月投毒影响
——托管的价值，就是把纪律交给专业团队执行。
阿里云 AI 网关 Serverless 把门槛降到最低：
标准版 0 元起步
，
无实例费、按实际用量计费，适合试用和低流量业务；
企业版
面向正式生产，独立入口、自定义域名、99.95% SLA，实例费参考价 0.245 元/小时。引擎由平台构建、发布和升级，自定义插件在 WebIDE 开发、VPC 集群内构建，全程不经公网；一键对接 WAF 与 AI 安全围栏，拦截注入攻击、识别提示词注入与敏感内容。

04
稳定性与可观测性：
生产业务的两个必答题
Cloud Native
安全与成本解决的是可用性问题，生产业务还需直面另外两项考验：模型服务发生抖动时如何保障业务连续性，以及 Token 消耗的去向能否清晰归因。
AI Fallback：主模型限流，业务不中断。
模型服务限速、抖动是常态。在网关侧开启 Fallback 后，主模型返回 4xx/5xx、流式首包超时，网关自动切换到你预配置的备用模型，应用侧无感知。一个 Model API 可以配多级备用链路，逐级降级；备用模型、顺序、超时阈值都是控制台上的一次配置变更，不用每个应用各写一套重试逻辑，也不用为改一个兜底策略发一次版。
Agent 管理与 FinOps 会话观测：把每一分 Token 对应到任务。
企业里的 Agent 越来越多——Claude Code、Codex、百炼、Dify、自研应用——最终可能共用同一个 Model API，接口维度的汇总数据只能回答“用了多少”，说不清来自哪个 Agent、哪项任务、哪一轮。AI 网关的 Agent 管理为每个 Agent 建立统一身份，一张拓扑图看清“谁在访问它、它访问哪些模型”；用量统计按 Agent 维度聚合请求数、Token、错误率、Fallback 率和 P95 延迟，并给出每日智能洞察。还能按 Session（会话）→ Turn（轮次）→ Model Call（模型调用）三层下钻：哪次会话消耗高、时间花在哪一步、缓存命中率多少，逐条可查。优化模型选择、压缩上下文、调整工具调用流程，从“凭感觉”变成“看数据”。
05
智能路由：
将模型选择从应用代码中剥离
Cloud Native
当入口安全、运行稳定与成本透明三项前提均已就位，关注点便回到全文开头的核心问题：每一次请求应当交给哪个模型处理。
常见做法各有难处：全丢给旗舰模型，成本和限流压力一路涨；在应用代码里手写选择逻辑，模型一换、价格一变就得发版；每次请求都重新判断，Agent 工具链又会“中途换脑”，缓存失效、时延徒增。
阿里云 AI 网关把“选模型”收进智能路由，思路是
先满足任务，再优化偏好
：
先按协议、模态、工具能力、上下文容量和可用状态排除不合格候选，结合 ModelCard 元数据（结构化的能力事实，不靠模型名猜）形成“足以完成任务”的候选集，再应用你选择的 Profile 产出唯一决策。四种 Profile 开箱即用：
综合均衡
（balanced）、
成本优先
（cheap）、
速度优先
（fast）、
质量优先
（quality）——能力是硬约束，价格只是偏好，cheap 不会为了便宜选能力不够的模型。
Agent 时代，知道什么时候“不重选”同样重要。
上下文保持机制（ContextHold）按对话节奏决定何时换模型：同一轮任务里的连续工具调用不换；用户发来新消息才重新判断；上下文压缩后原选择仍适用就保持。实测一次 40 次请求的编码任务，35 次（87.5%）直接沿用已有选择——既保住 KV Cache 的上下文亲和，又免去每次工具往返重走路由的时延。
换模型会不会把缓存省的钱赔回去？
账算得清：缓存损失只发生在切换后的第一次请求，一轮调用 n 次，整轮命中率下降不超过 1/n；往便宜模型切时，旧上下文全价重处理往往比贵模型读缓存还便宜（10 万 token 前缀：旗舰读缓存约 0.10 美元 vs 经济模型全价重处理约 0.019 美元）。对照实验中，混合路由相比全程旗舰
省下 91%～92%
，
且这是经济模型缓存命中为 0 的最保守情况；测算下来，旗舰模型要降价约 95% 才能打平——因为便宜模型的账单大头在输出，缓存只给输入打折。
接入不需要新 SDK：控制台把 Model API 后端场景设为“智能路由”，配置候选模型（最多 5 个自定义候选，也可开启平台内置的经济/标准/旗舰档位），调用侧把
model
改成
auto/balanced
、
auto/cheap
、
auto/fast
或
auto/quality
即可；继续填具体模型名的请求完全旁路，原有行为不变。路由状态只保存有界任务摘要，不持久化完整 Prompt 和凭据。
06
结语：入口架构应该一次做对
Cloud Native
回看 LiteLLM 的 2026 年，攻击者集中瞄准 LLM 代理，根源在于这一架构位置本身的吸引力，与代码工程质量关系不大。此类结构性风险难以依靠补丁逐一消除，治理手段需要落在架构层：默认无权限的 Wasm 沙箱限定了恶意代码进入系统后的行动边界，不可变发布链路将其拦截在制品进入生产之前，运维纪律交由托管平台持续执行。在此之上，Fallback 与会话观测保障业务运行的连续性和透明度，智能路由则把节省下来的成本留在业务侧。
